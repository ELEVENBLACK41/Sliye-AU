## 2. 本阶段结论

第三阶段不是重新搭建一套 Agent Runtime，而是在第二阶段已经完成的 Thread、Run、Event、租约、中心注册表和最小真实工具链之上，扩展一组窄、只读、受实时权限保护、可审计的决策过程工具。

阶段结束时，用户应能够用自然语言指定一项有权访问的决策，Agent 完成实体发现和安全消歧，然后读取核心决策过程信息，并按当前纳入 profile 读取项目/群组层级、过程事件或可见讨论消息，最后给出明确说明证据边界的简短回答。每次工具调用都必须保存工具状态和实际读取来源，不能通过模型上下文、旧 Thread 或工具原始输出绕过当前权限。

### 2.1 第三阶段负责什么

- 补齐中心工具注册表的风险、权限、结果上限、超时、重试和并行治理合同；
- 按实际纳入范围扩展 `AiSourceDependency` 对提案、投票轮次、决策事件、讨论消息及后续层级来源的登记与实时可见性判定；
- 以“解释一项决策如何形成”的最小闭环为首批交付方向，优先覆盖提案、投票汇总和正式决议；工具数量不设固定上限，按真实问题和评测收益按需增加；
- 继续复用已经完成的 `findDecisionCandidates` 和 `getDecisionContext`，但补齐项目、公共群、小组群的绑定信息，不重复实现已经存在的实体发现逻辑；
- 按需增加项目/群组发现、范围内决策列表、事件和讨论查询工具；每个新增工具都必须单独经过契约、权限、来源、结果上限和评测门禁；
- 使用当前项目锁定的 Vercel AI SDK 7 官方 Loop、上下文和超时能力，显式限制步骤、工具暴露和单次调用预算；
- 使用 AI SDK Mock、真实 PostgreSQL 隔离测试库和脱敏 Fixture 验证工具选择、参数、权限、来源、空结果、超时和安全停止；
- 复用第二阶段现有 AI 工作台、POST 直出流、GET 恢复流和工具卡完成真实脱敏数据验收，不重新设计页面。

### 2.2 第三阶段明确不负责什么

- 不实现创建提案、发起投票、提交选票、形成决议或修改业务数据的写工具；
- 不实现第 4 阶段的审批状态、写操作门禁和完整 Prompt Injection 防线；
- 不生成第 5 阶段的正式 `AiCitation`、Claim 级引用或 Evidence Receipt；
- 不把简单结构化查询伪装成第 6 阶段的中文关键词检索基线，不声明 Recall@K；
- 不引入 `pgvector`、Embedding、Rerank、Redis、BullMQ、Workflow、MCP、通用 Agent 框架或独立向量库；
- 不实现跨进程续跑、多实例调度、生产级长任务恢复或第 10 阶段的上下文压缩；
- 不新增通用 SQL、HTTP、Shell、代码执行或任意 URL 工具；
- 不重做 AI 页面，不新建 admin 端，不扩展到决议后的任务分配和执行跟踪；
- 旧 `/api/chat` Mock 路由已按确认移除；不在该路由或 Web 占位文件中继续扩展工具，第三阶段工具统一通过 NestJS 中心注册表交付。

## 4. 已确认的核心设计

### 决策层级与绑定模型

项目是决策的顶层协作容器，项目下有一个公共讨论群和多个小组讨论群；决策始终归属于一个项目。你的产品语义中，“项目级决策”不是脱离群组的决策，而是绑定项目公共群、供项目内跨部门成员共同参与的公共决策；“小组决策”则绑定某个私有小组群。当前数据模型使用 `projectId` 表达项目归属，使用 `areaId` 指向绑定的讨论分区，`DiscussionArea.type` 决定绑定目标是公共群还是私有小组群。

对 Agent 暴露的产品范围语义统一使用：

```text
PROJECT        // 项目级公共决策；areaId 指向当前项目的 PUBLIC 讨论群
GROUP          // 小组决策；areaId 指向当前项目的 PRIVATE 讨论群
```

`areaId = null` 只作为旧数据的 `LEGACY_UNBOUND` 兼容状态，不是新的产品范围；在未完成历史数据回填前，读取时可按项目级公共决策兼容展示，但不得继续创建新的无群决策。当前代码创建逻辑拒绝把决策绑定到 `PUBLIC` 分区，并在 `areaId` 省略时写入项目级语义，这需要在领域绑定对齐步骤中修正。

项目范围的可见性由项目成员关系保证，因此可以覆盖多个部门；当前 `Decision.deptId` 只表示牵头/责任部门，不代表共同参与的全部部门。若未来需要审计“哪些部门共同参与”，应新增明确的部门关系或快照，不应让 Agent 从用户当前部门反推历史事实。

项目、群组和范围字段只是查询过滤和消歧信息，不是权限凭据。模型传入的 `projectId`、`areaId` 或 `scope` 必须由 NestJS 重新验证真实归属、群组类型和当前用户可见性。

### 层级目标解析状态机

层级发现不是让模型自由组合 ID，而是一个可审计的候选收敛过程：

1. 用户同时提供决策名称和项目/群组线索时，先调用 `findDecisionCandidates`，将名称和范围线索作为过滤条件；
   - 这类组合查询可以直接在一次 NestJS 授权查询中完成，不要求先单独解析项目或群组；如果返回多个决策候选，再用候选中的项目/群组信息追问，不把范围名称当作已确认 ID；
2. 用户只提供项目名称时，按需调用 `findProjectCandidates`；项目候选不唯一就先追问，不进入决策读取；
3. 用户提供项目和群组名称但没有决策名称时，先解析项目，再调用 `findDiscussionGroupCandidates`；群组候选不唯一就先追问；
4. 项目和群组解析完成后，调用 `listDecisionsByScope` 获取范围内决策，或调用带范围过滤的 `findDecisionCandidates` 查找具体决策；
5. 只有 `decisionId` 候选恰好唯一时，才允许 `getDecisionContext` 及其后续提案、投票、决议、事件和讨论工具；
6. 所有 ID 必须来自本 Run 的已授权查询结果。模型自行填写的 `projectId`、`areaId` 或 `decisionId` 只能作为待验证输入，不能直接读取业务数据；
7. 如果用户直接提供了明确且有权访问的决策标识符，可以跳过项目/群组名称发现，但 `getDecisionContext` 仍必须返回并校验真实绑定范围。

该状态机只约束工具选择和消歧，不替代 NestJS 的实时权限判断；候选为空、重名或范围不一致时统一返回安全追问，不泄漏无权对象是否存在。

### 4.1 请求与执行链路

```text
Browser / AI Workspace
  -> Next.js POST 直出流或恢复入口
  -> Web Agent Runtime（模型、Loop、动态工具适配）
  -> NestJS 内部 Runtime API（服务身份 + Run 租约）
  -> AiToolRegistryService / AiToolInvocationService
  -> 领域工具执行器（输入收窄、实时权限、输出映射）
  -> decisions / projects 业务域只读查询服务
  -> Prisma / PostgreSQL
  -> AiToolCall + AiSourceDependency + AiEvent
  -> 模型得到受控结构化结果
```

浏览器不直接获得内部 Runtime Token，也不直接调用工具执行接口；Web Runtime 不访问 Prisma；AI 模块不复制 decisions/projects 的业务权限逻辑。

### 4.2 中心工具注册表治理合同

第三阶段需要在现有 descriptor 上补齐下列信息。字段名在 3.1-A 评审后冻结，本文描述语义，不提前把示例名称当成已落地代码：

| 治理项 | 目的 | 第一版规则 |
| --- | --- | --- |
| 稳定名称和说明 | 让模型、审计和测试使用同一工具身份 | lowerCamelCase；说明必须包含何时使用、何时不要使用和返回数据含义 |
| 输入与输出 Schema | 在执行前拒绝非法参数，并限制模型看到的结构 | 闭合对象；禁止未声明字段；输出只含白名单字段 |
| 访问模式 | 防止只读阶段混入写操作 | 全部固定为 `READ` |
| 风险等级 | 为第 4 阶段审批和策略扩展保留统一判断 | 第三阶段全部为低风险只读，但仍显式登记 |
| 授权责任边界 | 避免工具目录复制一套静态业务权限规则 | Descriptor 不声明用户权限；Thread 所有者由 NestJS 现取，真实数据范围由业务域每次计算 |
| 来源类型 | 约束工具必须登记哪些实际业务来源 | descriptor 声明允许类型，executor 返回实际读取来源 |
| 结果上限 | 控制数据库、模型上下文和页面审计体积 | 至少包含最大条数和最大字符数；在数据库查询与输出映射两处共同执行 |
| 超时 | 避免单工具拖垮整轮 | descriptor 记录单工具上限；Runtime 把上限交给 AI SDK/fetch 中止链路 |
| 重试 | 防止模型错误调用被基础设施无限重放 | 第一版工具执行器不自动重试；模型请求级重试继续由模型注册表控制 |
| 并行策略 | 防止有依赖工具被同一步错误并行 | 只有目标已唯一发现且彼此无输出依赖的只读工具可并行 |
| 发现依赖 | 防止模型猜测 `decisionId` | 继续使用 `discoveryRequirement` 并由 NestJS 强制验证 |

注册表元数据本身不是权限边界。即使模型绕过描述或同时发起多个调用，NestJS 仍须通过当前用户、Run、租约和来源权限完成最终拒绝。

### 4.3 工具执行器与业务域分层

每个工具遵循相同分层：

1. descriptor 定义稳定名称、用途、窄 Schema 和治理元数据；
2. AI 工具执行器只负责输入校验、从 Run 派生授权上下文、调用业务域查询、映射窄输出和列出来源；
3. decisions/projects 业务域查询服务负责 Prisma、实时数据范围、排序、分页或 `take` 上限；
4. `AiToolInvocationService` 负责租约、调用审计、来源登记和稳定错误收敛；
5. Web Runtime 只把 descriptor 转换成 AI SDK 工具并调用 NestJS，不感知 Prisma 模型。

提案、投票、决议和事件优先在 decisions 域新增单一职责的 `DecisionProcessEvidenceQueryService`，集中提供受权限保护、字段白名单和有界的过程证据查询。该服务不返回 AI SDK 类型，也不拼 Prompt。讨论消息继续由 projects/chat 业务域提供有界查询，避免 decisions 或 ai 模块直接跨域访问 `DiscussionMessage`。

### 4.4 工具输出与来源依赖

工具执行结果继续使用“窄输出 + 实际来源列表”结构：

```text
AiToolExecutionResult<TOutput>
  -> output: 允许进入模型上下文的结构化数据
  -> sources: 本次实际读取的稳定来源类型、主键和安全标签
```

来源登记规则：

- 所有目标工具至少登记父级 `DECISION`；
- 提案工具登记每条实际返回的 `DECISION_PROPOSAL`；
- 投票工具登记每个实际返回的 `DECISION_VOTE_ROUND`，绝不登记或返回个人 `DecisionBallot`；
- 决议工具登记每条实际返回的 `DECISION_RESOLUTION`；
- 事件工具登记每条实际返回的 `DECISION_EVENT`；
- 讨论工具登记每条实际返回的 `DISCUSSION_MESSAGE`；
- 空结果仍登记已成功读取的父级 `DECISION`，证明本轮访问了哪个授权目标；
- 来源 label 只保存安全名称，不保存正文、票数明细、私聊内容或其他敏感字段；
- `CITED` 来源和正式引用协议仍留到第 5 阶段，本阶段只登记 `READ`。

### 4.5 来源实时可见性

新增来源类型后，历史读取必须继续 fail closed：

| 来源类型 | 实时可见性判定 |
| --- | --- |
| `DECISION` | 复用现有 decision 数据范围 |
| `DECISION_PROPOSAL` | 先确认提案存在，再通过其父级 decision 的当前权限判定 |
| `DECISION_VOTE_ROUND` | 先确认轮次存在，再通过父级 decision 权限判定；不读取 ballot 身份 |
| `DECISION_RESOLUTION` | 复用现有 resolution 可见性判定 |
| `DECISION_EVENT` | 通过父级 decision 权限判定；若事件关联受限会议或消息，输出前还需满足对应来源权限或隐藏受限字段 |
| `DISCUSSION_MESSAGE` | 同时满足父级 decision 可见、讨论分区可见、消息未删除；私有区和会议消息按当前成员关系重新判定 |

来源被删除、用户失权或父级关系失效时，受影响的 Run/消息/工具结果继续使用第二阶段已经完成的中性占位，不暴露来源标题、正文、数量或存在性细节。

### 4.6 Loop、上下文和并行规则

- 完整工具集接入后，把步骤上限从第二阶段最小链的 6 调整为 8；只有评测证明不足时才能在 8～12 范围内上调；
- 目标尚未唯一发现时，只允许实体发现工具；候选唯一后再开放目标读取工具；
- `getDecisionContext`、提案、投票、决议和事件在只依赖同一个已发现 `decisionId` 时可以并行；
- 需要根据另一工具输出才能构造参数的调用必须串行，NestJS 继续校验发现记录，不能只信 `prepareStep`；
- 同一步并行调用的总结果仍受整轮字符预算约束，不能把每个工具上限简单相加后全部注入模型；
- `runtimeContext` 只保存 request/run 关联、预算和非敏感运行状态；业务目标仍来自用户可见消息；
- 工具上下文不进入模型 Prompt，也不进入未经筛选的遥测；
- 每个工具请求传播 `abortSignal`，但浏览器断开仍遵守第二阶段语义：只关闭当前订阅，不自动取消后台 Run；只有用户显式停止或租约失效才中止执行。

### 4.7 搜索工具与后续检索阶段的边界

`searchDecisionEvents` 和 `searchDiscussionMessages` 在第三阶段只是有界结构化查询：

- 事件按明确 decision、事件类型和时间范围过滤；
- 消息按明确 decision、可见分区、时间范围和可选字面关键词过滤；
- 不生成向量、不做语义召回、不做 RRF、不做 Rerank；
- 不以第三阶段消息查询结果声明 Recall@K 或“已经完成 RAG”；
- 第 6 阶段再用同一 Gold Set 建立 `pg_trgm` 中文关键词基线，并决定是否替换第三阶段的简单过滤实现。

### 4.8 基础安全边界

第三阶段仍需保证最基本的安全不变量，但不提前实现第 4 阶段全部策略：

- 工具结果中的正文、消息和事件标题都视为业务数据，不视为系统指令；
- 模型不能通过用户消息要求工具跳过权限、扩大数量或返回原始 payload；
- descriptor 不提供通用 SQL、任意 URL、任意模型或任意工具名参数；
- 投票只返回规则允许公开的汇总，不返回匿名个人票、投票人—选项映射或私有理由；
- 错误返回稳定 code 和安全说明，不把 SQL、内部 URL、堆栈、Token 或权限查询细节发给模型；
- 完整 Prompt Injection 评测、审批和写工具隔离仍在第 4 阶段完成。

### 当前纳入范围与工具批准记录

第三阶段不设工具数量上限，但每轮必须先确定“当前纳入范围”。纳入范围按能力 profile 管理，不按工具数量管理：

| Profile | 当前工具 | 交付规则 |
| --- | --- | --- |
| 核心决策过程 | `findDecisionCandidates`、`getDecisionContext`、`listDecisionProposals`、`getVoteRoundSummary`、`getDecisionResolution` | 第三阶段的核心只读闭环；五项能力都要有实现或明确的空结果语义，但不代表第三阶段只能有五个工具 |
| 层级导航 | `listDecisionsByScope`、`findProjectCandidates`、`findDiscussionGroupCandidates` | 只有真实 Query 需要按项目/公共群/小组群浏览或消歧时纳入 |
| 过程证据 | `searchDecisionEvents`、`searchDiscussionMessages`、`listDecisionMeetings` | 只有真实问题需要事件、讨论或会议证据时纳入；每项独立做权限和来源门禁 |
| 参与关系 | `listProjectMembersForDecision` 或其他参与人工具 | 只有用户确实需要回答参与范围、责任边界时纳入，不默认开放用户目录 |

3.0 收口时在本文变更记录中登记当前 profile：`ENABLED` 表示本阶段必须完成，`DEFERRED` 表示保留候选但不阻塞本阶段。新增或切换工具必须记录问题样例、现有工具不足原因、输入/输出、权限、来源、上限、测试和 migration 影响，并由老大确认后才能进入 `ENABLED`。

### 工具数量与按需扩展规则

第三阶段不以“新增五个工具”作为交付目标。工具注册表是开放集合，但开放不代表任意堆叠：

- 每个工具必须对应一个明确、可复现的用户问题，不能只为不同问法创建重复工具；
- 每个工具必须有窄输入、窄输出、实时权限、来源登记、条数/字符上限、超时和稳定错误；
- 只有当现有工具组合无法清晰回答、或者工具选择/延迟/Token 评测证明拆分有收益时，才增加新工具；
- 新工具按“契约 → 业务域有界查询 → 执行器 → 注册 → Mock/真实脱敏评测”逐步加入，不能一次注册整套目录；
- 工具数量不影响阶段完成判定；阶段完成依据是当前纳入范围的工具全部通过对应门禁，并完成至少一条核心只读闭环；
- 工具组可以按真实场景逐步启用。未被实际问题证明有价值的候选工具可以暂缓，不算阶段缺陷。

#### 工具新增准入记录

新增工具前至少需要满足以下一种证据，并在本文“当前纳入范围”或变更记录中登记：

- 出现一个现有工具组合无法回答的明确用户问题；
- 同类问题至少出现两条代表性 Query，且拆成独立工具能降低歧义、权限风险、延迟或 Token 成本；
- 现有工具因结果上限、来源类型或业务权限无法安全承载该问题；
- 阶段评测出现可重复失败，且增加工具比扩展现有工具更容易验证和回滚。

登记内容至少包括问题样例、为什么现有工具不够、候选输入/输出、权限和来源、上限、测试样例以及是否需要 migration。工具由老大确认纳入当前阶段后再进入实现；没有这条记录的工具可以保留为候选，不得直接注册到 Runtime。

根据当前业务层级，后续可按需增加以下工具，而不是现在全部实现：

| 按需工具 | 触发场景 | 说明 |
| --- | --- | --- |
| `listDecisionsByScope` | “项目 A 公共群有哪些决策”“小组群最近有哪些决策” | 按项目、群组和范围列出有界决策摘要；不是 `findDecisionCandidates` 的空查询变体 |
| `findProjectCandidates` | 用户只提供项目名称，未提供具体决策 | 负责项目名称消歧；是否纳入需先证明存在跨项目问法 |
| `findDiscussionGroupCandidates` | 一个项目下有多个同名或相近群组 | 负责公共群/小组群消歧；必须返回群组类型，不返回私有成员名单 |
| `listProjectMembersForDecision` | 用户询问决策参与范围或责任边界 | 只在产品确实需要回答参与人问题时加入，不默认开放用户目录 |
| `listDecisionMeetings` | 用户需要解释决策关联的会议过程 | 需先确认会议权限和来源类型，不与讨论消息搜索混为一谈 |

项目/群组发现工具如果最终作为模型回答依据，需要在来源类型评审中决定是否登记 `PROJECT`、`DISCUSSION_AREA`；如果只作为路由和消歧元数据，也必须经过权限过滤，不能因为“不生成引用”就绕过授权。

### 5.1 `listDecisionProposals`

- 执行器只接收已经通过发现状态机唯一确认的 `decisionId`；项目、群组和范围过滤不放进本工具，避免一个工具同时承担目标解析和过程读取；
- 不返回创建者邮箱、权限、完整用户对象、会议隐私字段或未声明关系；
- 查询必须在数据库层 `take`，不能先加载全部提案再在 AI 工具中截断；
- 开放、已接受、已关闭状态均可查询，默认按创建时间正序保证过程解释稳定；
- 描述为空时返回 `null`，超长时返回明确 `truncated: true`，不能静默伪装成完整正文；
- 空列表是成功结果，不转换为内部异常。

### 5.2 `getVoteRoundSummary`

- DRAFT 轮次只返回配置，不返回不存在的实时结果；
- OPEN 轮次遵守现有业务语义，不返回实时选项票数；
- CLOSED 轮次只返回允许公开的汇总、有效票数、法定人数和结果状态；
- 匿名轮次永远不返回 voterId、用户名称、个人选项、个人理由或可反推身份的排序；
- 非匿名轮次第三阶段同样不返回个人选票，避免把“可见”误当“Agent 必须读取”。

### 5.3 `getDecisionResolution`

- 只返回当前用户有权访问的决议；
- 返回 `ACTIVE/SUPERSEDED/REVOKED` 等稳定状态和 `supersedesId` 关系，但不自动把被替代决议当成当前结论；
- 正式正文可截断用于模型上下文，工具结果必须标记是否截断；
- 若决议引用提案或投票轮次，只返回安全标识和标题，不展开第二份未登记来源正文。

### 5.4 `searchDecisionEvents`

- 只返回事件类型、标题、发生时间、公开参与者展示名和经过白名单映射的关联标识；
- 不返回 Prisma `payload/before/after` 原始 JSON，避免泄漏变更前数据和内部字段；
- 不返回 `DecisionTask` 执行状态作为当前产品主线；若事件类型属于当前冻结的执行闭环，默认排除；
- 时间、类型和游标排序确定性一致，便于后续时间线回放复用。

### 5.5 `searchDiscussionMessages`

- 只查询与目标 decision 明确关联且当前用户可见的消息；
- 删除消息、系统保留但普通用户不可读的内容、无权私有分区和无权会议消息必须在数据库查询阶段排除；
- 不返回 reply 整棵树、附件原文、完整用户对象或未脱敏的审计字段；
- 简单关键词只做字面过滤，不声称语义搜索；
- 返回结果按时间与主键稳定排序，支持有界游标，不允许一次读取全部讨论历史。

## 7. 数据模型、迁移与部署顺序

### 7.1 预计数据变化

第三阶段根据实际纳入的工具扩展 `AiSourceType` enum，不新增 AI 或业务表；未纳入的候选工具不提前增加来源类型。下列是可能用到的候选集合，不代表必须在一条 migration 中全部加入：

```text
DECISION
DECISION_PROPOSAL
DECISION_VOTE_ROUND
DECISION_RESOLUTION
DECISION_EVENT
DISCUSSION_MESSAGE
```

3.2-0 的决策绑定语义对齐属于业务模型前置修正，与 AI 来源 enum migration 分开评审：新建 `PROJECT` 决策必须绑定当前项目的公共讨论群，新建 `GROUP` 决策必须绑定私有小组群。历史 `areaId = null` 记录先按 `LEGACY_UNBOUND` 兼容读取，是否批量回填到公共群要先盘点数据、验证权限影响，再生成独立 migration；不能在工具开发中静默改写。

如果实施中发现必须新增表、改变业务实体关系或保存大段工具原文，必须停止当前步骤并重新评审，不能顺势扩大 migration。

### 7.2 兼容性

- 现有 `DECISION`、`DECISION_RESOLUTION` 行保持不变；
- 新建决策只允许绑定同项目的 `PUBLIC` 或 `PRIVATE` 讨论分区；历史 `areaId = null` 仅作为兼容状态读取，不作为新的产品范围；
- 新 enum 值只扩展允许集合，不重写历史来源；
- 新代码不得在数据库 migration 尚未应用时写入新 enum 值；
- contracts、Prisma schema、generated client、来源映射和可见性服务必须在同一个目标步骤内保持一致；
- 旧 Web Runtime 只消费工具 descriptor，不读取 Prisma enum，因此数据库扩展不要求 UI 协议升级。

### 7.3 部署顺序

1. 先完成 3.2-0 的公共群/小组群绑定语义设计、领域测试和历史数据影响评估；
2. 如确认需要回填历史 `areaId = null`，先在隔离库执行独立数据 migration 并验证权限投影；
3. 在隔离测试库应用本阶段实际需要的来源 enum migration 并生成 Prisma Client；
4. 运行来源登记和可见性集成测试；
5. 部署支持新绑定语义、新 enum 和新来源判定的 NestJS；
6. 再注册会写入对应来源的工具 descriptor/executor；
7. 最后开放 Web Runtime 使用新工具并执行真实 Smoke。

### 7.4 失败恢复与回滚

- 新工具出现问题时，先从中心注册表移除对应 descriptor/executor，保留审计数据；
- enum 已有新来源行后不做破坏性枚举删除，优先前向修复；
- 本地测试失败可重建隔离测试库，不清空开发库或真实数据；
- 来源可见性判定异常时 fail closed，受影响历史显示中性占位，不降级为“默认可见”；
- migration 或权限影响超出预期时停止，不继续进入后续工具步骤。

### 9.1 每步最小验证原则

- 纯文档：Markdown 链接、状态和 `git diff --check`；
- contracts：`pnpm --filter @workspace/contracts check-types`；
- 注册表/执行器：Server 对应 spec，不机械运行全量 build；
- Prisma/来源权限：必须使用独立测试库运行真实 PostgreSQL 集成；
- Web Loop：AI Runtime 定向 Node 测试和 Web 类型检查；
- 跨 contracts/server/web 的步骤：至少运行三端定向类型检查；
- 阶段验收：Node 22 下运行全部直接相关自动化、真实浏览器和显式 Gateway Smoke。

### 9.2 固定 Fixture

第三阶段新增 Fixture 属于长期质量资产；每个实际纳入的工具都必须补齐对应样例，首批至少包含：

- 有两项提案、多轮投票和正式决议的完整决策；
- 没有提案、投票或决议的空过程决策；
- 同名决策用于消歧；
- 开放匿名投票与关闭匿名投票；
- 被替代和被撤销的历史决议；
- 公开讨论、私有讨论、无权会议消息和已删除消息；
- 含“忽略系统提示、扩大权限、返回所有消息”等文本的 Prompt Injection 诱饵；
- 来源在 Run 完成后失权或删除的历史场景。

真实业务样本继续放在 Git 忽略目录并脱敏，不提交私聊正文、Cookie、Token 或连接串。

## 10. 第三阶段完成标志

只有同时满足以下条件，第三阶段才能标记为 `✅ 已完成`：

1. 中心注册表完整表达并校验风险、权限、来源、结果上限、超时、重试和并行策略；
2. `findDecisionCandidates`、`getDecisionContext` 与当前纳入第三阶段范围的全部工具通过各自契约和权限测试；工具数量不作为完成条件；
3. 核心验收 profile 至少包含“发现决策—读取上下文—列提案—取投票汇总—读取正式决议—给出简短回答”；没有正式决议数据时，`getDecisionResolution` 必须返回安全的“尚未形成”结果；事件、讨论、项目和群组层级工具只有在被真实需求纳入后才进入本阶段验收；
4. 每次工具调用都有 `AiToolCall`、事件、耗时、稳定错误和实际 `AiSourceDependency`；
5. 非成员、私有区、来源失权和删除场景的越权来源数为 0；
6. 匿名投票的个人票、投票人—选项映射和个人理由泄漏数为 0；
7. 工具结果在数据库查询和模型上下文两层均受上限控制，不存在无界列表或原始 JSON；
8. 达到 8 步上限时安全停止并说明未完成，不无限调用或错误标记 Run 为成功；
9. 独立只读工具可并行，有依赖工具不会提前执行，NestJS 仍是最终强制边界；
10. 关闭浏览器再打开后，工具调用、来源和最终回答可通过第二阶段历史链路恢复；
11. 现有 AI 工作台、POST 直出流和 GET 恢复流无视觉或功能回退；
12. 没有引入第三阶段非目标中的写工具、RAG、Workflow、Redis、MCP 或新 Agent 框架；新增工具均有明确需求和独立验收记录。
13. 新建 `PROJECT` 决策实际绑定项目公共群，新建 `GROUP` 决策实际绑定私有小组群；历史 `areaId = null` 数据有兼容或回填结果记录。

单独完成某一个工具或模型在一次 Smoke 中成功调用多个工具，只代表对应增量完成，不代表第三阶段完成；未被真实需求纳入范围的候选工具可以继续保持 `⬜ 未开始`。

## 11. 主要风险与处理

### 11.1 来源类型扩展被低估

风险：只新增工具查询，却没有同步来源 enum 和可见性判定，导致历史回答在失权后仍可读。

处理：3.2 作为所有新增来源工具的前置地基；任何新来源没有可见性测试就不得注册工具。

### 11.2 AI SDK 同一步默认并行

风险：模型在同一步调用多个工具，单纯记录 `allowParallel` 不会自动阻止执行。

处理：NestJS 继续强制发现依赖；必要时使用 `prepareStep.activeTools` 控制暴露；并行测试验证调用顺序和审计一致性。

### 11.3 自定义 Schema 系统继续膨胀

风险：为事件和讨论搜索不断增加自定义字段类型，最终重复实现 JSON Schema。

处理：3.6-A 设正式门禁；复杂输入改用 AI SDK 支持的 Zod/JSON Schema，不新增第二套协议。

### 11.4 讨论查询偷跑到 RAG

风险：简单关键词过滤被包装成“已经完成语义检索”，导致后续指标和架构失真。

处理：第三阶段只提供明确过滤、有界字面查询；第 6 阶段再建立关键词 Recall 基线。

### 11.5 工具返回过大

风险：各工具分别满足上限，但并行合计仍挤爆上下文或拖慢模型。

处理：工具级条数/字符上限加整轮结果预算；超预算时优先缩减低价值字段，不静默丢失关键来源标识。

### 11.6 投票隐私误用现有 DTO

风险：直接复用面向页面的投票 DTO，把个人投票、实时票数或内部关系带进模型。

处理：单独定义 AI 窄输出；开放和匿名规则进入固定 Fixture；ballot 不进入工具查询和来源类型。

### 11.7 为官方抽象做无收益重构

风险：在新增业务工具同时迁移 `ToolLoopAgent`、UI Transport 或 Workflow，扩大回归面。

处理：保留当前官方支持的 `streamText` Loop；任何抽象替换必须单独证明能删除复杂度并通过现有流式/持久化回归。

### 11.8 遗留 Mock 与真实工具混淆

风险：继续在 Web 占位工具中扩展功能，形成第二套不可审计工具链。

处理：旧 `/api/chat` Mock 路由已经移除；第三阶段只通过 NestJS 中心注册表交付，Web 占位文件不作为真实工具注册入口。
