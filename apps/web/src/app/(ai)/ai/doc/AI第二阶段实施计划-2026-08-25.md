## 2. 本阶段结论

第二阶段不只为“单项决策聊天”建立状态表，而要为最终的全局 Decision Agent 建立可扩展的运行基建。

最终 Agent 需要能够：

- 查询当前用户有权访问的项目、决策、提案、投票、会议、通话和参与关系；
- 回答“哪些决策讨论过 Redis”“最长会议开了多久”“上次和谁通话”“有哪些投票需要我参与”等跨模块问题；
- 比较多个项目或提案，并明确比较维度和证据来源；
- 根据讨论、提案、投票、会议和正式决议生成可交互的决策线路图；
- 后续在明确审批后执行受控业务操作，但第二阶段仍只实现只读闭环；
- 对所有工具调用、来源、状态变化、错误、取消和模型用量进行审计。

因此，`AiThread` 不能永久强制绑定单个 `Decision`。所有 Thread 都是归属于创建用户的普通 AI 会话，可以保存一个可选的入口业务上下文。没有入口上下文表示用户从 AI 工作台直接创建会话，不代表拥有全局数据权限；入口上下文只帮助 Agent 理解用户当前所在页面，不是权限凭证，也不限制用户在授权范围内进行跨项目查询。

### 2.1 第二阶段负责什么

- 修正并冻结 Thread、Message、Run、Event 的共享语义；
- 建立 PostgreSQL 权威状态和事务约束；
- 建立幂等、单 Thread 单活跃 Run、事件序号、执行租约和迟到写入 fencing；
- 用一个真实、只读、受 NestJS 权限保护的业务工具验证运行闭环；
- 提供 Thread 历史、消息分页、停止、重试、归档和恢复接口；
- 按照现有 AI 工作台的第一版 UI 和视觉风格，接入真实 Thread、Run、工具、引用与页面状态；
- 支持刷新恢复、同进程断线事件补拉和确定性故障收敛。

### 2.2 第二阶段明确不负责什么

- 不在本阶段完成全部项目、投票、会议、提案和检索工具；
- 不实现“讨论过 Redis”所需的完整关键词、向量和混合检索；
- 不引入 `pgvector`、Redis、BullMQ、Rerank 或独立向量数据库；
- 不实现写业务数据的 Agent 操作；
- 不实现跨进程续跑、Serverless 长任务恢复和生产级端到端取消；
- 不实现会话全文搜索、文件夹、共享会话、物理删除或复杂保留策略；
- 不重新设计或替换现有 AI 工作台，不为了接入旧业务逻辑而回退到旧版 Card、列表、表单或布局；
- 不因为已有网页检索或 Mock 工具而把第二阶段视为真实业务闭环完成。

这些能力分别在后续只读工具、结构化证据、关键词检索、向量检索、生产加固和审批阶段继续实现。

## 4. 已确认的核心设计

以下内容来自当前产品目标，先作为第二阶段不可破坏的设计约束。

1. Agent 的默认产品形态是跨业务数据助手，不是单 Decision Chat。
2. Thread 可以携带默认业务上下文，但上下文不是权限凭证，也不是永久检索边界。
3. 用户可以在无固定业务上下文的工作台会话中查询多个项目，也可以从项目、决策或会议页面带入口上下文进入。
4. 所有工具调用都由 NestJS 根据当前用户和实时业务关系重新鉴权。
5. 精确事实通过结构化领域工具查询，不能让模型或向量检索猜测。
6. 讨论、消息和会议转写等非结构化证据在后续检索阶段接入。
7. PostgreSQL 保存 Thread、Run、事件和审计事实；Redis 将来只承担任务调度、缓存和实时协调。
8. 同一 Thread 第一版同时最多一个非终态 Run。
9. Run 进入终态后不可回退；重试必须创建新 Run 并关联旧 Run。
10. 浏览器断开不等于取消。事件先持久化，再推送给订阅者。
11. 模型生成物默认为草稿，不得自动写入正式业务记录。
12. 第二阶段只开放一个真实只读工具验证闭环，不提前铺开完整工具集。
13. 当前 AI 工作台第一版 UI 是第二阶段的数据接入和视觉验收基线；后续只按现有风格填充真实能力，不另起一套页面设计。

## 5. Thread 可选入口上下文修正方案

### 5.1 推荐的共享语义

建议只定义可选的入口上下文，不再使用容易被误解为“全局权限”的 `GLOBAL Thread` 或 `GLOBAL` 上下文类型。具体字段命名仍需在 2.1 评审后冻结：

```ts
type AiThreadEntryContext =
  | { type: 'PROJECT'; projectId: number }
  | { type: 'DECISION'; decisionId: number }
  | { type: 'MEETING'; meetingId: number };
```

| 会话入口 | 保存的入口上下文 | 是否允许跨上下文查询 |
| --- | --- | --- | --- |
| AI 工作台 | 无 | 允许查询当前用户有权访问的多个业务范围 |
| 项目页面 | `PROJECT` + 一个项目 | 允许，Agent 必须明确工具参数并重新鉴权 |
| 决策页面 | `DECISION` + 一项决策 | 允许，不要求为了比较另一项决策强制新建 Thread |
| 会议或通话页面 | `MEETING` + 一场会议/通话 | 允许，会议只作为默认焦点 |

第一版不单独建立 `CALL` 上下文。当前通话和预约会议都由 `MeetingSession.kind`、状态和参与记录区分，Thread 使用 `MEETING` 上下文即可。

### 5.2 推荐的数据表达

为保留数据库外键完整性，不推荐使用无外键约束的通用 `contextType + contextId` 多态引用。当前推荐：

- `contextProjectId`、`contextDecisionId`、`contextMeetingId` 均可空；
- 三个字段全部为空表示从 AI 工作台直接创建、没有固定入口上下文；
- 数据库 migration 增加 CHECK 约束，保证三个入口上下文最多只有一个非空；
- NestJS 根据 Decision、Meeting 的真实关系解析所属项目或私有区域，不信任浏览器补充的派生 ID；
- contracts 使用可选的可判别联合表达创建请求，避免前端构造非法组合。

示意契约：

```ts
type AiThreadEntryContext =
  | { type: 'PROJECT'; projectId: number }
  | { type: 'DECISION'; decisionId: number }
  | { type: 'MEETING'; meetingId: number };

type CreateAiThreadRequest = {
  entryContext?: AiThreadEntryContext;
  message: string;
  idempotencyKey: string;
};
```

### 5.3 上下文与权限必须分离

- 上下文用于 Prompt 提示、UI 标识和默认工具参数；
- 权限由每次 NestJS 工具调用和每次历史读取实时判断；
- 没有入口上下文不代表可读取全库，只表示工具可以在当前用户授权范围内跨项目查询；
- 浏览器传入的 `projectId`、`decisionId`、`meetingId` 都不能直接成为权限过滤条件；
- 系统管理员也继续遵守现有私有区域访问规则，不自动穿透私有讨论。

### 5.4 权限变化后的历史策略

原总路线图采用“任一来源失权就锁定整个 Thread”，该规则只适合单 Decision Thread，不适合无固定业务上下文、可能包含多个项目证据的工作台会话。当前推荐改为：

- 每个 Run/助手消息保存实际读取和实际引用的来源依赖；
- 读取历史时重新校验这些来源；
- 某个 Run 的任一来源失权时，锁定或隐藏该 Run 对应的助手消息、工具结果和引用，显示中性占位，不泄漏原标题或摘要；
- 无固定业务上下文的工作台会话不因单个来源失权而整体报废，仍可继续提出与其他授权数据有关的问题；
- 带项目、决策或会议入口上下文的 Thread 在根上下文本身失权时整体锁定，且不能继续发送消息；
- 权限撤销发生在 Run 执行中时，NestJS 使当前租约失效并收敛 Run，撤销后的事件和结果不得继续落库或推送；
- 是否允许来源恢复后自动解锁对应消息，需要在 2.5 前单独评审。

这套策略需要 `AiSourceDependency` 或等价关系表支持，不能只在 Message JSON 中保存不可查询的来源列表。

## 6. Run 状态与并发不变量

当前状态集合继续保留：

```text
QUEUED
  -> RUNNING
  -> CANCELLED

RUNNING
  -> WAITING_APPROVAL
  -> CANCELLATION_REQUESTED
  -> COMPLETED
  -> FAILED

WAITING_APPROVAL
  -> RUNNING
  -> CANCELLATION_REQUESTED

CANCELLATION_REQUESTED
  -> CANCELLED
  -> FAILED

CANCELLED / COMPLETED / FAILED
  -> 不允许继续转换
```

第二阶段必须同时保证：

- 同状态重复写入由事务幂等层处理，不放宽状态机；
- 同一 Thread 最多一个 `QUEUED/RUNNING/WAITING_APPROVAL/CANCELLATION_REQUESTED` Run；
- `completed -> running` 永远非法；
- 重试创建新 Run，旧 Run 保持原终态；
- 取消与完成竞争只能产生一个终态；
- 进入 `CANCELLATION_REQUESTED` 或租约失效后，迟到文本、工具结果和完成状态均被拒绝；
- `GET /stream` 只订阅或补拉，不得创建 Run 或启动执行器；
- Node 进程内注册表只保存临时执行句柄，不是权威状态。

## 8. 数据模型与约束草案

下表是实施分配，不代表字段已经冻结。字段级设计必须在对应增量开始前再次评审。

| 模型 | 引入步骤 | 核心职责 | 关键约束 |
| --- | --- | --- | --- |
| `AiThread` | 2.2-A | 用户会话、默认上下文、归档状态、当前活跃 Run | 所有者必填；上下文组合合法；活跃 Run 与 Thread 一致 |
| `AiMessage` | 2.2-A | 用户/助手展示消息 | Thread 内稳定顺序；客户端请求幂等；正文不能承担工具原文存储 |
| `AiRun` | 2.2-A | 一次执行、状态、模型、用量、取消、重试、租约 | 单 Thread 单非终态 Run；终态不可回退；重试关联旧 Run |
| `AiEvent` | 2.2-A | 流式恢复和审计事件 | `(runId, sequence)` 唯一；只追加，不原地改写历史事件 |
| `AiStep` | 2.4 | 一次模型步骤和停止原因 | `(runId, sequence)` 唯一；保存受控 Token 摘要 |
| `AiToolCall` | 2.4 | 工具输入摘要、状态、耗时和错误 | 不保存密钥；大结果保存来源引用和受控摘要 |
| `AiSourceDependency` | 2.4/2.5 | Run 实际读取或引用的业务来源 | 可按来源反查受影响 Run；区分读取与引用用途 |
| `AiCitation` | 2.4/后续阶段 | 生成内容与稳定来源的映射 | 引用只能指向本 Run 的允许来源集合 |
| `AiApproval` | 第 4 阶段 | 写操作或高风险工具审批 | 第二阶段不提前启用空审批流程 |

### 8.1 单活跃 Run 的数据库约束

`AiThread.activeRunId` 可以作为事务比较更新和快速读取指针，但只靠应用判断不够。2.2-A 需要评审以下方案：

1. `activeRunId` 可空唯一外键，并由所有状态事务同步维护；
2. PostgreSQL 对 `AiRun(threadId)` 增加“非终态状态”的部分唯一索引，作为最终并发硬门禁；
3. 同时使用两者时，必须在同一事务更新并增加一致性对账，避免形成两个权威来源。

当前推荐同时保留快速指针和部分唯一索引，但在 migration 前必须确认 Prisma 迁移、测试数据库和回滚方案能够稳定支持自定义 SQL。

### 8.2 事件序号

- 不使用 `SELECT MAX(sequence) + 1`；
- 推荐在 `AiRun` 保存下一事件序号，通过原子更新分配单个序号或序号区间；
- `AiEvent` 使用 `(runId, sequence)` 唯一约束兜底；
- 事件批量追加和 Run 状态更新是否共用事务，由 2.2-B 的性能与一致性测试决定；
- 前端只使用服务端事件序号，不使用本地数组下标恢复流。

### 8.3 幂等键

至少需要区分：

- 创建 Thread：当前用户 + 创建请求键；
- Thread 内发送消息：Thread + 当前用户 + 消息请求键；
- 重试 Run：旧 Run + 当前用户 + 重试请求键。

同一键但请求正文、上下文或目标不同应返回 `AI_IDEMPOTENCY_CONFLICT`，不能静默重放旧结果。幂等键保留时间、字段落点和是否单独建立请求表仍是 2.2-B 的待决策项。

## 9. 最小浏览器 API 草案

以下是 Next.js BFF 对浏览器提供的目标契约。BFF 不拥有最终权限和状态规则。

- `POST /api/ai/threads`：接收可判别上下文、首条非空消息和幂等键，原子创建 Thread、Message 和 Run；
- `GET /api/ai/threads`：按游标、归档状态和可选上下文过滤当前用户 Thread；
- `GET /api/ai/threads/:threadId`：获取 Thread 元数据和最近 Run 摘要；
- `GET /api/ai/threads/:threadId/messages`：游标分页获取消息及允许展示的工具和引用数据；
- `POST /api/ai/threads/:threadId/messages`：原子创建用户消息和 Run；
- `GET /api/ai/threads/:threadId/stream?runId=...&afterSequence=...`：订阅或补拉已有 Run，绝不启动新执行器；
- `POST /api/ai/runs/:runId/stop`：请求停止当前 Run；
- `POST /api/ai/runs/:runId/retry`：从失败或取消 Run 创建关联的新 Run；
- `PATCH /api/ai/threads/:threadId`：只允许重命名、归档和恢复归档。

NestJS 还需要受服务身份保护的内部执行契约，用于领取、续租、事件追加、工具来源登记和终态写入。浏览器不得直接调用这些内部接口。
