## 2. 本阶段结论

第二阶段不只为“单项决策聊天”建立状态表，而要为最终的全局 Decision Agent 建立可扩展的运行基建。

最终 Agent 需要能够：

- 查询当前用户有权访问的项目、决策、提案、投票、会议、通话和参与关系；
- 回答“哪些决策讨论过 Redis”“最长会议开了多久”“上次和谁通话”“有哪些投票需要我参与”等跨模块问题；
- 比较多个项目或提案，并明确比较维度和证据来源；
- 根据讨论、提案、投票、会议和正式决议生成可交互的决策线路图；
- 后续在明确审批后执行受控业务操作，但第二阶段仍只实现只读闭环；
- 对所有工具调用、来源、状态变化、错误、取消和模型用量进行审计。

因此，`AiThread` 不绑定也不保存项目、决策、会议等业务上下文。Thread 只是归属于创建用户的对话容器；用户在消息中直接说明要查询、比较或绘制的对象，Agent 再通过发现/搜索工具定位真实业务实体。目标重名或信息不足时，Agent 返回候选项并追问，不把猜测写成隐含会话状态。

### 2.1 第二阶段负责什么

- 修正并冻结 Thread、Message、Run、Event 的共享语义；
- 建立 PostgreSQL 权威状态和事务约束；
- 建立幂等、单 Thread 单活跃 Run、事件序号、执行租约和迟到写入 fencing；
- 支持同一 Thread 的用户输入持久化排队，以及“调整方向”触发的当前 Run 有序取消与优先续跑；
- 用一条最小真实、只读、受 NestJS 权限保护的业务工具链（实体发现 + 决策上下文读取）验证运行闭环；
- 提供 Thread 历史、消息分页、停止、重试、归档和恢复接口；
- 按照现有 AI 工作台的第一版 UI 和视觉风格，接入真实 Thread、Run、工具、引用与页面状态；
- 支持刷新恢复、同进程断线事件补拉和确定性故障收敛。

### 2.2 第二阶段明确不负责什么

- 不在本阶段完成全部项目、投票、会议、提案和检索工具；
- 不实现“讨论过 Redis”所需的完整关键词、向量和混合检索；
- 不引入 `pgvector`、Redis、BullMQ、Rerank 或独立向量数据库；
- 不实现写业务数据的 Agent 操作；
- 不实现跨进程续跑、Serverless 长任务恢复和生产级端到端取消；
- 不实现多个 Run 并行执行、跨 Thread 全局调度或把新指令直接注入已经开始的模型请求；
- 不实现会话全文搜索、文件夹、共享会话、物理删除或复杂保留策略；
- 不重新设计或替换现有 AI 工作台，不为了接入旧业务逻辑而回退到旧版 Card、列表、表单或布局；
- 不因为已有网页检索或 Mock 工具而把第二阶段视为真实业务闭环完成。

这些能力分别在后续只读工具、结构化证据、关键词检索、向量检索、生产加固和审批阶段继续实现。

## 4. 已确认的核心设计

以下内容来自当前产品目标，先作为第二阶段不可破坏的设计约束。

1. Agent 的默认产品形态是跨业务数据助手，不是单 Decision Chat。
2. Thread 不保存项目、决策、会议等业务上下文，也不提供手动选择业务目标的入口。
3. 用户直接通过自然语言说明目标；Agent 使用发现/搜索工具解析实体，遇到歧义时展示候选项并追问。
4. 所有工具调用都由 NestJS 根据当前用户和实时业务关系重新鉴权。
5. 精确事实通过结构化领域工具查询，不能让模型或向量检索猜测。
6. 讨论、消息和会议转写等非结构化证据在后续检索阶段接入。
7. PostgreSQL 保存 Thread、Run、事件和审计事实；Redis 将来只承担任务调度、缓存和实时协调。
8. 同一 Thread 第一版同时最多一个占用执行门禁的非终态 Run；用户消息可以持久化排队，但排队项不等同于并发 Run。
9. “调整方向”不是把文本硬插入已开始的模型请求，而是持久化一条高优先级用户消息、请求取消当前 Run，并在取消收敛后优先创建下一次 Run。
10. Run 进入终态后不可回退；重试必须创建新 Run 并关联旧 Run。
11. 浏览器断开不等于取消。事件先持久化，再推送给订阅者。
12. 模型生成物默认为草稿，不得自动写入正式业务记录。
13. 第二阶段只开放“实体发现 + 决策上下文读取”这一条最小真实只读工具链验证闭环，不提前铺开提案、投票、讨论、会议或检索工具集。
14. 当前 AI 工作台第一版 UI 是第二阶段的数据接入和视觉验收基线；后续只按现有风格填充真实能力，不另起一套页面设计。

## 5. Agent 目标解析与来源权限方案

### 5.1 Thread 只保存对话状态

`AiThread` 只保存所有者、标题、当前活跃 Run、归档时间和审计时间，不保存项目、决策、会议或通话 ID。创建请求也只包含首条用户消息与幂等键：

```ts
type CreateAiThreadRequest = {
  message: string;
  idempotencyKey: string;
};
```

页面将来若提供“询问 AI”快捷入口，也只负责生成一条明确的自然语言消息，例如“总结决策《缓存方案评审》的 Redis 讨论”，而不是给 Thread 设置隐藏业务状态。这样后续追问和跨项目比较都由可见对话承载，不产生过期的默认目标。

### 5.2 Agent 如何定位业务目标

1. Agent 从当前用户消息和必要的最近对话中提取实体名称、类型、时间范围和查询意图；
2. 精确 ID 已在消息可见内容中给出时，可直接调用对应的窄工具；
3. 只有名称或描述时，先调用受权限保护的发现/搜索工具获得候选实体；
4. 唯一候选才继续查询；多个合理候选或置信度不足时，返回不泄漏越权数据的候选项并追问；
5. 工具结果返回稳定来源标识，回答只引用本次 Run 实际获准读取的来源。

第二阶段只实现一条最小真实工具链，不在 2.1 提前实现完整的目标解析器或搜索工具。2.4 允许用户直接以自然语言给出决策名称、别名或可见标识符，Agent 先调用 `findDecisionCandidates`，唯一命中后再调用 `getDecisionContext`；重名或信息不足时只展示允许访问的候选并追问。明确 `decisionId` 可以作为测试 Fixture，但不是产品输入要求。第 3 阶段在这条链路上扩展跨业务实体发现与更多结构化工具；讨论正文、会议转写等非结构化证据的“讨论过 Redis”类问题，再由第 6、7 阶段检索能力逐步补齐。

### 5.3 权限与历史保护

- 当前用户身份只进入 Agent Runtime 的受控执行上下文，不作为模型可以伪造的工具参数；
- 每次 NestJS 工具调用都根据当前用户和实时业务关系鉴权，不信任模型或浏览器传入的派生范围；
- 每个 Run/助手消息登记实际读取和实际引用的来源依赖；
- 读取历史时重新校验这些来源；某个来源失权时，只锁定或隐藏受影响的助手消息、工具结果和引用，并显示中性占位；
- Thread 本身没有业务根上下文，因此不会因单个项目、决策或会议失权而整体锁死，用户仍可继续询问其他有权数据；
- 权限撤销发生在 Run 执行中时，NestJS 使当前租约失效并以 `SOURCE_ACCESS_REVOKED` 收敛 Run，撤销后的事件和结果不得继续落库或推送；
- 系统管理员也继续遵守现有私有区域访问规则，不自动穿透私有讨论；
- 是否允许来源恢复后自动解锁对应历史，需要在 2.5 前单独评审。

这套策略需要 `AiSourceDependency` 或等价关系表支持，不能只在 Message JSON 中保存不可查询的来源列表。

## 6. Run 状态与并发不变量

当前状态集合继续保留：

```text
QUEUED
  -> RUNNING
  -> CANCELLED

RUNNING
  -> WAITING_APPROVAL
  -> CANCELLATION_REQUESTED
  -> COMPLETED
  -> FAILED

WAITING_APPROVAL
  -> RUNNING
  -> CANCELLATION_REQUESTED

CANCELLATION_REQUESTED
  -> CANCELLED
  -> FAILED

CANCELLED / COMPLETED / FAILED
  -> 不允许继续转换
```

第二阶段必须同时保证：

- 同状态重复写入由事务幂等层处理，不放宽状态机；
- 同一 Thread 最多一个 `QUEUED/RUNNING/WAITING_APPROVAL/CANCELLATION_REQUESTED` Run；
- `completed -> running` 永远非法；
- 重试创建新 Run，旧 Run 保持原终态；
- 取消与完成竞争只能产生一个终态；
- 进入 `CANCELLATION_REQUESTED` 或租约失效后，迟到文本、工具结果和完成状态均被拒绝；
- `GET /stream` 只订阅或补拉，不得创建 Run 或启动执行器；
- Node 进程内注册表只保存临时执行句柄，不是权威状态。

### 6.1 排队消息与活跃 Run 的分工

- `AiRun` 只表示一次已经获准执行的工作，不用多个 `QUEUED` Run 充当输入队列；活跃 Run 存在时，后续用户输入先以可审计的 `AiMessage` 排队状态落库。
- 每个 Thread 的排队顺序由数据库事务分配的单调序号决定，不能依赖浏览器时间、内存数组或事件到达顺序；相同幂等键只能得到同一条排队消息。
- 当前 Run 进入终态后，分发事务只能原子领取该 Thread 队首的一条普通排队消息，创建新的 `AiRun(QUEUED)` 并同步维护 `activeRunId`；任何时刻仍只能存在一个非终态 Run。
- 普通再次发送不打断当前回答，消息显示为“排队中”；刷新、重连和服务重启后仍可按持久化顺序恢复展示与领取。
- “调整方向”持久化为高优先级排队消息，并把当前 Run 置为带 `USER_REDIRECTED` 原因的取消请求。只有当前 Run 以唯一终态收敛后，定向消息才可被领取；租约与 fencing 必须拒绝取消后的迟到文本、工具结果和完成写入。
- 多次“调整方向”采用“最新定向请求覆盖全部尚未领取的旧用户输入”的已确认策略：此前普通和定向消息均保留审计记录并转为 `SUPERSEDED`，不再等待执行；只有最新定向请求保持待领取。该语义由用户显式选择“调整方向”触发，不依赖模型猜测消息是否相关。

### 8.1 单活跃 Run 的数据库约束

`AiThread.activeRunId` 可以作为事务比较更新和快速读取指针，但只靠应用判断不够。2.2-A 需要评审以下方案：

1. `activeRunId` 可空唯一外键，并由所有状态事务同步维护；
2. PostgreSQL 对 `AiRun(threadId)` 增加“非终态状态”的部分唯一索引，作为最终并发硬门禁；
3. 同时使用两者时，必须在同一事务更新并增加一致性对账，避免形成两个权威来源。

当前推荐同时保留快速指针和部分唯一索引，但在 migration 前必须确认 Prisma 迁移、测试数据库和回滚方案能够稳定支持自定义 SQL。

### 8.2 事件序号

- 不使用 `SELECT MAX(sequence) + 1`；
- 推荐在 `AiRun` 保存下一事件序号，通过原子更新分配单个序号或序号区间；
- `AiEvent` 使用 `(runId, sequence)` 唯一约束兜底；
- 事件批量追加和 Run 状态更新是否共用事务，由 2.2-B 的性能与一致性测试决定；
- 前端只使用服务端事件序号，不使用本地数组下标恢复流。

### 8.3 幂等键

至少需要区分：

- 创建 Thread：当前用户 + 创建请求键；
- Thread 内发送消息：Thread + 当前用户 + 消息请求键；
- 重试 Run：旧 Run + 当前用户 + 重试请求键。

同一键但请求正文不同应返回 `AI_IDEMPOTENCY_CONFLICT`，不能静默重放旧结果。幂等键保留时间、字段落点和是否单独建立请求表仍是 2.2-B 的待决策项。

### 8.4 输入队列的候选字段

2.2-C 开始前再冻结具体命名。当前候选是为用户消息增加 `dispatchState`（如 `QUEUED`、`DISPATCHED`、`SUPERSEDED`）、`queueSequence` 和 `submissionMode`（如 `NORMAL`、`STEER`），并在 Thread 上保存下一可分配队列序号。这里的排队状态不替代 `AiRun.status`：前者描述一条用户输入是否待分发，后者描述已经创建的实际执行。

若保留“最新定向请求替代旧定向请求”策略，旧请求必须转为可见、可审计的 `SUPERSEDED` 或等价状态，而不是删除消息；最终枚举名称、索引和保留策略由 2.2-C migration 评审确定。

## 9. 最小浏览器 API 草案

以下是 Next.js BFF 对浏览器提供的目标契约。BFF 不拥有最终权限和状态规则。

- `POST /api/ai/threads`：接收首条非空消息和幂等键，原子创建 Thread、Message 和 Run；
- `GET /api/ai/threads`：按游标和归档状态过滤当前用户 Thread；
- `GET /api/ai/threads/:threadId`：获取 Thread 元数据和最近 Run 摘要；
- `GET /api/ai/threads/:threadId/messages`：游标分页获取消息及允许展示的工具和引用数据；
- `POST /api/ai/threads/:threadId/messages`：接收用户消息、幂等键和提交模式（普通发送或“调整方向”）；原子入队并返回投递状态、队列位置以及已创建的 Run（如有）；
- `GET /api/ai/threads/:threadId/stream?runId=...&afterSequence=...`：订阅或补拉已有 Run，绝不启动新执行器；
- `POST /api/ai/runs/:runId/stop`：请求停止当前 Run；
- `POST /api/ai/runs/:runId/retry`：从失败或取消 Run 创建关联的新 Run；
- `PATCH /api/ai/threads/:threadId`：只允许重命名、归档和恢复归档。

NestJS 还需要受服务身份保护的内部执行契约，用于领取、续租、事件追加、工具来源登记和终态写入。浏览器不得直接调用这些内部接口。
