## 1. 先给结论

本计划中的“回滚”不是把仓库退回某个旧提交，也不是删除 AI 模块后从空目录重写，而是：

> 保留已经验证的业务权限、模型治理、会话数据、来源审计、业务工具、UI 和评测资产；用 Vercel 官方 Agent、UI Message Stream 与客户端状态能力替换自研的模型执行调度、文本事件持久化、POST/GET 双流协议、事件归约、租约和进程内恢复基础设施。

迁移采用**旁路建立、逐项接入、主链切换、停止旧写入、观察后删除**的顺序。任何步骤失败，都优先回到上一条已经通过验证的链路，不通过 Git reset、历史 migration 修改或一次性删表回退。

当前建议：

1. 暂停旧第三阶段 3.1-A 及后续新工具开发；
2. 暂停修补现有文本持久化队列容量问题，除非它阻塞收敛验证所需的旧链路对照；
3. 先以现有 `findDecisionCandidates` 和 `getDecisionContext` 完成官方 Runtime 纵向 Spike；
4. Spike 通过后再迁移真实工作台、历史持久化、来源和控制能力；
5. 旧 Web Stream 和 Nest Runtime 只在新主链通过验收后删除；
6. 旧数据库表和字段最后通过新的前向 migration 处理，不修改历史 migration。

## 3. 为什么需要收敛

### 3.1 产品目标已经超过单项 Decision Agent

NextNest 需要的是一个面向当前用户全部授权业务数据的 Workspace Agent。它未来需要支持但不限于：

- 查询当前用户拥有或参与的项目、决策、投票和会议数量；
- 查询等待当前用户参与的投票或协作事项；
- 对多个项目、决策、提案、投票与决议做比较分析；
- 解释某项提案为什么被拒绝或某项决议如何形成；
- 在用户有权访问的聊天和会议记录中查找人物、主题和时间；
- 结合业务讨论、会议上下文和用户补充，对 Redis 等技术方案做分析；
- 在证据不足时明确追问，不把模型常识伪装成业务事实。

这些能力真正需要投入的复杂度是：业务工具、实体消歧、实时权限、结构化查询、混合检索、证据引用、上下文预算和评测，而不是重新实现通用 Agent Loop、UI Stream、客户端消息状态和长任务调度。

### 3.2 当前运行时复杂度已经产生反向成本

当前 AI 生产代码排除文档与测试后约有：

| 范围 | 文件数 | 代码行数 | 主要职责 |
| --- | ---: | ---: | --- |
| Web AI | 52 | 5968 | Runtime、Stream、Hook、服务、UI、模型治理 |
| Server AI | 51 | 6341 | Thread/Run/Event、租约、工具、来源、查询 |
| AI contracts | 13 | 1001 | 状态、命令、事件、Runtime、工具契约 |
| 合计 | 116 | 13310 | 不含评测、测试和计划文档 |

其中自定义 Web Runtime、Hooks、Services 和 Utils 约 4289 行。现有文本直出采用 `live-delta` 立即展示、异步写 `AiEvent`、再把 `ai-event` 作为确认返回浏览器；当模型 delta 生产速度超过串行 HTTP + PostgreSQL 持久化速度时，会触发有界队列失败并中止正常回答。这说明通用流式基础设施已经开始占用本应投入业务 Agent 的开发与排障成本。

### 3.3 当前 Git 和数据库不适合历史回滚

- AI 能力从 2026-07 权限体系开始逐步接入，并非一个独立提交；
- 2026-08-20 之后有几十个连续 AI 提交，模型治理、UI、持久化和工具能力交错演进；
- 已有 `add_ai_thread_run_persistence`、`add_ai_input_queue`、`add_ai_step_tool_call_source`、`add_ai_thread_pinned_at` 等 migration；
- 直接回退旧提交会同时丢失 UI、权限复用、来源、评测和数据兼容；
- Git 回滚代码不会安全回滚已经应用的数据库 migration。

因此，历史回滚风险高于渐进收敛，不作为本计划方案。

## 4. 收敛目标与非目标

### 4.1 目标

1. 使用 `ToolLoopAgent` 作为默认 Agent Loop；
2. 使用 AI SDK 官方 `tool`、Zod Schema、`stopWhen`、`prepareStep`、`runtimeContext` 和 `toolsContext`；
3. 使用 `createAgentUIStreamResponse` 或当前安装版本对应的官方 UI Message Stream Response；
4. 使用 `useChat + DefaultChatTransport` 管理客户端消息、流状态、停止和重试；
5. 使用 `InferAgentUIMessage<typeof agent>` 保持工具消息端到端类型安全；
6. 继续使用 AI Elements 的 Conversation、Message/MessageResponse、Tool、Sources 和 PromptInput；
7. 继续通过 AI Gateway 完成模型路由、回退、用户归因、标签、用量和成本观测；
8. NestJS 继续作为身份、权限、业务事实和来源可见性的最终裁决者；
9. PostgreSQL 继续保存业务事实、Thread、Message、Run 摘要和来源依赖；
10. 普通短时聊天不再逐模型 delta 写 PostgreSQL 事件；
11. 真正需要长时间、暂停/恢复、自动重试或崩溃恢复的任务，再独立评估 Vercel Workflow；
12. 收敛后能够继续扩展项目、决策、投票、会议、聊天和 RAG 能力，而不重新扩建第二套通用 Agent Runtime。

### 4.2 非目标

- 不把仓库 reset、rebase 或 checkout 到旧 AI 提交；
- 不在首轮删除旧代码、旧表、旧字段或历史 migration；
- 不在收敛步骤同时实现全部 Workspace Agent 工具；
- 不在收敛步骤提前实现 pgvector、Rerank、Redis、Workflow 或 Vercel Queues；
- 不新增 admin 端；
- 不扩展到决议后的任务分配、进度跟踪和结果验收；
- 不为了使用 Vercel 产品而无收益地堆叠基础设施；
- 不让浏览器、模型输入或工具参数决定最终用户权限；
- 不把聊天记录、会议转写或检索正文当作系统指令；
- 不在同一轮同时切换 Runtime、重写 UI、迁移数据库并删除旧链路。

## 5. 不可破坏的业务与安全不变量

收敛只能替换通用运行机制，不能削弱以下边界：

1. **NestJS 最终鉴权。** Agent 工具不得信任模型传入的 `userId`、`projectId`、`areaId` 或权限声明；
2. **先权限过滤，再查询或召回。** 结构化 SQL、关键词和向量召回都必须在当前授权范围内执行；
3. **匿名投票保护。** 不返回匿名 ballot、投票人—选项关系或个人匿名理由；
4. **精确事实由工具计算。** 数量、状态、时间、参与资格和投票结果不得由模型从列表自行推断；
5. **来源实时可见。** 历史消息展示引用时仍需重新判断当前权限、删除状态和来源生命周期；
6. **生成物默认是草稿。** 当前 Agent 不自动写入正式决议或修改业务数据；
7. **业务证据与模型常识分开。** 技术分析必须区分“基于项目讨论”与“基于通用技术原则”；
8. **检索正文是不可信输入。** Prompt Injection 文本不能扩大工具权限或改变系统指令；
9. **工具窄而有界。** 不开放通用 SQL、任意 HTTP、Shell 或代码执行；
10. **无证据允许拒答。** 不为完整性编造业务过程；
11. **越权泄漏零容忍。** 任一越权来源直接判定迁移门禁失败；
12. **既有数据可恢复。** 切换期间不得静默丢失 Thread、Message、Run 终态或来源依赖。

## 6. 目标架构

```text
Browser
  useChat + DefaultChatTransport
  AI Elements Conversation / Message / Tool / Sources / PromptInput
        |
        | UI Message Stream
        v
Next.js Agent Route
  ToolLoopAgent
  stopWhen / prepareStep.activeTools
  runtimeContext / toolsContext
  AI Gateway
        |
        | typed narrow tools
        v
NestJS BFF / Domain APIs
  current user identity
  ProjectAccessService / AuthorizationService
  bounded structured queries
  source visibility
        |
        +--> PostgreSQL facts
        +--> pg_trgm / pgvector retrieval（后续阶段）

onEnd / lifecycle callbacks
        |
        +--> AiMessage UI parts / final content
        +--> lightweight AiRun summary
        +--> AiToolCall audit summary
        +--> AiSourceDependency / Citation
```

`onEnd` 和生命周期回调只负责把结果提交给 Next.js BFF/NestJS 持久化接口；Web Agent Route 不直接读取 Prisma。NestJS 仍是 Thread、Message、Run 摘要、工具审计和来源依赖的最终写入边界。

### 6.1 普通请求与长任务分界

| 场景 | 默认运行方式 | 原因 |
| --- | --- | --- |
| 数量、状态、待参与项查询 | `ToolLoopAgent` 单次请求 | 短时、结构化、可快速完成 |
| 单项或少量决策分析 | `ToolLoopAgent` 多工具 Loop | 官方 Loop 足够，无需耐久工作流 |
| 聊天/会议语义搜索 | `ToolLoopAgent` + Retrieval Tool | 检索是工具，不等于长任务 |
| 多个项目的大范围报告 | 达到真实时长和恢复需求后评估 Workflow | 可能跨多个步骤且超出请求生命周期 |
| Embedding 全量重建 | 后续 Workflow/Queue 专项 | 需要重试、进度和后台执行 |
| 写工具等待人工批准 | 先用 AI SDK Tool Approval；长时间暂停再用 Workflow Hook | 避免先建设完整状态机 |

Workflow 当前未作为依赖安装。任何引入都必须单独说明收益、Vercel 绑定、部署配置、测试成本和非 Vercel 环境影响，并由老大确认。

## 9. 数据兼容与迁移策略

### 9.1 `AiMessage` 目标形态

当前 `AiMessage` 只保存 `role + content`，不能完整表达 AI SDK UIMessage 的 text、tool、source、reasoning 和自定义 data parts。收敛期间需评估以下两种方案：

| 方案 | 说明 | 建议 |
| --- | --- | --- |
| 增加 `parts Json?`、`metadata Json?` | 保留现有结构化字段，同时保存官方 UI parts | 推荐，兼容成本较低 |
| 单独新增消息 Part 表 | 每个 Part 独立行 | 当前不推荐，复杂度和查询成本高 |

兼容规则：

- 历史只有 `content` 的消息加载时映射为单个 text part；
- 新消息优先读取 `parts`，`content` 保留纯文本投影用于搜索、列表预览和兼容；
- 保存前使用当前 AI SDK `validateUIMessages` 校验包含工具、自定义 data 和 metadata 的消息；
- 不把密钥、Cookie、内部服务 Token、完整敏感工具输出写入 parts；
- 工具大结果继续通过受控摘要和来源引用持久化。

### 9.2 旧 Run/Event 数据

- 已存在的 `AiRun/AiEvent/AiStep/AiToolCall/AiSourceDependency` 不重写；
- 新主链切换前保持旧读写兼容；
- 新主链稳定后先停止写 `AiEvent/AiStep/lease`，但保留读取；
- 观察期内历史 Thread 仍能通过原消息和最终 Run 状态展示；
- 确认无读取依赖后，再生成新的前向 migration 删除旧字段或表；
- 已应用 enum 值不做破坏性删除，优先保留或前向兼容；
- 任何数据清理前先统计行数、最后写入时间、引用方和恢复需求。

### 9.3 部署与回退原则

- Web 与 Nest 先兼容新旧两种消息读取；
- 新主链只在当前收敛分支验证，不立即影响旧分支；
- 主链切换发生在代码层，数据库先保持向后兼容；
- 如新链路失败，恢复旧 Route/Hook 即可，不需要数据库回滚；
- 旧表删除后不承诺自动回到旧 Runtime，因此删表是最后一个不可轻易回退的门禁；
- 本地测试只允许重建隔离测试库，不清空开发库和真实数据。

运行语义矩阵：

| 场景 | C6 第一版默认行为 | 执行句柄/幂等边界 |
| --- | --- | --- |

| 多标签页 | 同一 Thread 不重复发送同一幂等请求；观察行为由 `useChat`/Transport 负责 | 不恢复旧自研 `AiEvent.sequence` 协议 |
| 进程重启/多实例 | 第一版不承诺普通聊天继续生成 | 真实需求触发 Workflow 或其他耐久执行专项 |

回退：恢复旧控制端点；新消息格式保持兼容。

## 11. 收敛后的业务工具组织

收敛不要求一次实现全部工具，但目标工具应按能力 profile 管理，避免把所有工具永久暴露给模型。

| Profile | 代表问题 | 候选工具方向 |
| --- | --- | --- |
| Workspace Overview | 我有几个项目、决策、会议；有哪些待参与投票 | 用户工作区汇总、待参与事项 |
| Project | 项目有哪些成员、决策、最近讨论 | 项目发现、项目上下文、项目决策列表 |
| Decision Process | 决策如何形成、提案为何拒绝 | 决策上下文、提案、投票汇总、决议、事件 |
| Collaboration Search | 谁讨论过 Redis、在哪次会议提到 | 讨论/会议关键词或混合检索 |
| Comparative Analysis | 对比几个项目、决策、提案 | 复用读取工具，由 Agent 组合，不默认新增重复比较工具 |
| Technical Analysis | Redis 在当前需求里是否合适 | 业务证据检索 + 模型技术分析 + 明确证据边界 |

`prepareStep.activeTools` 应根据实体发现结果和当前 profile 控制工具集合。第一版保持单 Agent，不引入多 Agent；只有评测证明单 Agent 的工具选择、上下文或延迟无法接受时再评估拆分。

| 来源 | ToolCall 与 SourceDependency 对齐，历史实时隐藏 |
| 投票隐私 | 匿名 ballot、个人理由和投票映射泄漏为 0 |
| 断线 | 浏览器断开不造成未捕获异常，最终结果按约定保存 |
| 停止 | 主动停止与普通断开语义分离，部分结果不覆盖新消息 |
| 重试 | 新响应独立，旧失败记录保留，不重复提交业务工具 |
| 性能 | 首段可见时间、HTTP 请求数、数据库写入数优于旧链路 |
| Gateway | 当前配置模型真实 Smoke、用量、错误和标签正常 |
| 回退 | 主链切换前每步都有代码级回退点，不依赖数据库回滚 |

阶段验收至少包含以下真实脱敏 Query：

1. “查找某项我有权访问的决策，并说明基本情况”；
2. “当前证据中没有这个决策时，不要猜测”；
3. “同名决策存在时先追问，不直接读取任意一个”；
4. “直接给出无权 decisionId 时拒绝读取”；
5. “流式回答中出现工具调用时，工具卡与最终正文一致”；
6. “刷新后历史消息与来源展示一致”；
7. “来源删除或失权后，历史展示不泄漏正文”。

## 14. 主要风险与处理

### 14.1 把“官方化”误解为删除业务边界

风险：直接使用 `useChat` 后把权限、来源和审计当成 SDK 已经提供。

处理：SDK 只接管通用运行和 UI；NestJS 权限、来源、匿名投票和业务查询继续作为不可破坏门禁。

### 14.2 双链路长期共存

风险：Spike 与旧 Runtime 都继续开发，最终形成两套正式实现。

处理：C0 冻结旧 Runtime 扩建；C7 设主链切换；C8/C9 明确删除步骤和完成期限。

### 14.3 为了兼容旧状态搬回全部复杂度

风险：新链路重新实现队列、租约、事件游标和调整方向，失去收敛意义。

处理：只保留当前真实需要的发送、停止、失败、重试和历史；续播、排队、调整方向、崩溃恢复按真实需求后置。

### 14.4 UIMessage 数据膨胀或泄密

风险：完整工具输出、聊天正文或内部信息被直接存入 parts。

处理：parts 保存受控 UI 数据；大结果只存摘要和来源；敏感正文不进入消息历史；保存前校验。

### 14.5 过早引入 Workflow

风险：普通聊天也进入 Workflow，增加 Vercel 绑定、调试和部署成本。

处理：普通短时请求使用 ToolLoopAgent；只有真实长任务、暂停/恢复或崩溃恢复需求触发 Workflow 专项。

### 14.6 删除旧表后发现历史依赖

风险：旧 Thread 或排障工具仍读取 `AiEvent/AiStep`。

处理：先停写、统计、观察、查引用，再单独 migration；数据库删除永远晚于代码主链稳定。

### 14.7 收敛期间继续增加业务工具

风险：每个新工具都要同时适配新旧 Runtime，扩大迁移面。

处理：C0～C11 期间只保留两个 Spike 工具；除修复权限或数据正确性问题外，不增加新工具。

## 16. 完成标志

只有同时满足以下条件，本计划才能标记为 `✅ 已完成`：

1. 主工作台使用 `ToolLoopAgent + UI Message Stream + useChat + AI Elements`；
2. 普通文本生成不再逐 delta 写 `AiEvent`；
3. 主链不再依赖自定义 POST/GET 双流、live sink、文本队列和事件 reducer；
4. Thread、历史、置顶、重命名、归档和恢复没有功能回退；
5. 停止、失败、重试和断线符合 C6 冻结的产品语义；
6. 现有两个真实工具在官方链路下通过权限和参数测试；
7. ToolCall、SourceDependency、模型、用量和稳定错误仍可审计；
8. 非成员、私有区、来源失权、删除来源和匿名投票泄漏数为 0；
9. 新旧历史消息均能加载为合法 UIMessage；
10. 首段可见时间、请求数和数据库写入数不劣于旧链路，且不再出现文本持久化队列满导致正常回答失败；
11. 旧 Web Runtime 与客户端协议代码已经删除或明确没有主链引用；
12. NestJS 中无消费者的 Runtime 服务与端点已经移除；
13. 数据库旧结构已完成停写审计，删除与否有明确结果；
14. 未因收敛引入未经确认的 Workflow、Redis、Queues、admin 或执行闭环；
15. 总路线图和第三阶段已切换到“官方 Runtime 上扩展授权业务工具与检索”的新基线。
