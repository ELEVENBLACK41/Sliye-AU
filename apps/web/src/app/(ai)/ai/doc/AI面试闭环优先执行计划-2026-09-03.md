# NextNest AI 面试闭环优先执行计划

> 文档用途：在不迁移 AI Runtime 官方抽象的前提下，快速完成一条可演示、可验证、可解释的 Decision Agent 产品闭环。
> 文档状态：当前面试窗口执行基线 v0.1
> 制定日期：2026-09-03
> 适用范围：apps/web、apps/server、packages/contracts 的 AI 相关代码和文档
> 前置决策：继续使用当前 streamText + tools + stopWhen、Thread/Run/Event、租约/fencing、POST/GET 流和现有 AI 工作台；不执行 ToolLoopAgent、useChat、DefaultChatTransport 或 UI Message Stream 官方化迁移。

## 1. 先给结论

当前 AI 模块的基础设施已经足够支撑面试中的架构说明，但真实业务能力还没有穿过最后一公里。

当前优先级不再是继续完善 Runtime，而是完成下面这一条纵向闭环：

> 用户询问一项自己有权访问的决策是如何形成的，Agent 找到并确认目标，读取提案、投票汇总和正式决议，生成一份带可点击证据来源的过程说明草稿；整个过程只读、可停止、可刷新恢复，不能泄漏权限外数据或匿名个人选票。

这条闭环完成后，当前项目就具备独立的面试演示价值。关键词检索、向量 RAG、重排、Workflow 和写操作均不属于面试闭环的前置条件。

## 2. 当前基线判断

### 2.1 已具备且继续保留的能力

- AI SDK 7 的 streamText、工具调用、多步 stopWhen Loop 和 AI Gateway 模型治理。
- Thread、Run、Event、Step、ToolCall、SourceDependency 持久化模型。
- Run 租约、fencing、取消、幂等、重试、POST 直出流和 GET 恢复流。
- 现有 AI 工作台、Thread 列表、历史消息、工具卡和失败/取消状态。
- NestJS 最终权限判断、工具注册表、工具调用审计和来源失权投影。
- findDecisionCandidates 和 getDecisionContext 两个真实只读工具。
- 50 条中文 Gold Query、脱敏 Fixture、Mock 模型和确定性评测报告。

### 2.2 当前闭环缺口

| 缺口 | 当前情况 | 面试影响 |
| --- | --- | --- |
| 业务工具 | 真实工具只有决策发现和上下文读取 | 只能证明 Agent 找到了决策，不能解释决策过程 |
| 证据展示 | AiCitationList 当前为空输出 | 用户看不到回答依据，无法形成“可核验”卖点 |
| 来源类型 | 目前主要支持 DECISION、DECISION_RESOLUTION | 提案和投票来源无法精确展示 |
| Web 占位代码 | 存在未实现工具文件和全局 Registry 占位文件 | 容易让仓库显得没有收口 |
| 浏览器验收 | 第二阶段部分真实写操作和生命周期仍待确认 | 现场演示可能遇到状态或恢复问题 |
| 测试环境 | Web AI 定向测试已通过；Server 类型检查/评测受本地 TypeScript 加载问题阻塞 | 面试前必须让验证命令可复现 |

## 3. 本计划的产品目标

### 3.1 必须完成的用户故事

用户输入类似：

~~~text
帮我说明“供应商选择”这项决策是怎么形成的？
~~~

Agent 最少完成：

1. 调用 findDecisionCandidates 查找当前用户可访问的决策。
2. 只有候选唯一时，调用 getDecisionContext 获取决策基础事实。
3. 调用 getDecisionFormationEvidence 获取该决策的提案、投票汇总、正式决议和基础时间线。
4. 生成中文过程说明，明确区分已确认事实、证据不足和正式决议。
5. 在回答下方展示来源级证据卡片，支持跳转或显示来源不可用状态。

### 3.2 MVP 完成定义

以下条件全部满足，才算面试闭环完成：

- 唯一授权决策可以完成“发现 → 上下文 → 过程证据 → 回答”。
- 重名决策不会自动选择，必须返回候选并要求用户确认。
- 无结果、无正式决议和证据缺失时不会编造结论。
- 非成员或直接猜测 ID 不能读取业务数据。
- 投票只返回允许展示的汇总，不返回匿名个人选票和身份映射。
- 回答可以看到至少一组真实来源卡片。
- 来源失权或删除后，历史回答中的来源正文和定位信息被隐藏。
- 刷新、断线恢复、停止、失败和重试不破坏已有 Thread/Run 语义。
- Web AI 定向测试、Server AI 定向测试、类型检查和一次真实浏览器验收通过。

## 4. 明确不做

本计划执行期间，以下内容全部后置：

- 不迁移 ToolLoopAgent、useChat、DefaultChatTransport 或 UI Message Stream。
- 不重写当前 Runtime，不删除租约、fencing、队列、事件 reducer、POST/GET 流或数据库表。
- 不实现写工具、审批门禁、创建提案、发起投票、提交选票或形成正式决议。
- 不实现联网搜索；如果界面上的联网开关未接入，直接移除或隐藏。
- 不实现 searchDiscussionMessages，不把当前简单查询包装成 RAG。
- 不引入 pgvector、Embedding、RRF、Rerank、Redis、BullMQ、Workflow、MCP 或 LangGraph。
- 不新增多 Agent、独立向量数据库或通用 SQL/HTTP/Shell 工具。
- 不为了清理代码而进行大范围重构。
- 不新增 AiCitation 数据表；MVP 先使用来源级证据，Claim 级引用另立后续步骤。

## 5. 核心技术方案

### 5.1 Runtime 方案

继续沿用当前架构：

~~~text
Browser AI Workspace
  -> Next.js POST 直出流 / GET 恢复流
  -> 当前 Web Agent Runtime
  -> AI SDK streamText + tools + stopWhen
  -> NestJS 内部 Runtime API
  -> AI Tool Registry / Tool Invocation
  -> Decisions 业务域有界查询
  -> PostgreSQL
~~~

AI SDK 负责模型调用和工具循环，NestJS 负责身份、权限、业务事实、来源和审计，不能把最终权限判断交给模型。

### 5.2 工具方案

MVP 只暴露三个工具：

| 工具 | 职责 | 状态 |
| --- | --- | --- |
| findDecisionCandidates | 根据名称或可见标识符查找候选 | 已有 |
| getDecisionContext | 读取单项决策基础事实 | 已有 |
| getDecisionFormationEvidence | 读取提案、投票汇总、正式决议和有限时间线 | 本计划新增 |

getDecisionFormationEvidence 是面向单一产品用例的窄工具，不是通用“查询全部数据”工具。其内部可以复用或新增独立的提案、投票、决议查询方法，但对模型只暴露有界的过程证据结构。

### 5.3 过程证据输出建议

第一版只返回受限结构，不返回完整业务 DTO：

~~~ts
type DecisionFormationEvidence = {
  decisionId: number;
  proposals: Array<{
    id: number;
    title: string;
    description: string | null;
    status: string;
    createdAt: string;
    sourceId: string;
  }>;
  voteRounds: Array<{
    id: number;
    title: string;
    status: string;
    options: Array<{
      proposalId: number | null;
      label: string;
      voteCount: number | null;
    }>;
    sourceId: string;
  }>;
  resolutions: Array<{
    id: number;
    title: string;
    content: string;
    status: string;
    decidedAt: string;
    sourceId: string;
  }>;
  timeline: Array<{
    label: string;
    occurredAt: string;
    sourceId: string;
  }>;
  evidenceGaps: string[];
};
~~~

实际实现时应以当前 contracts 和 Prisma 类型为准，不直接复制上述示例类型。所有数组、描述和正文都必须在数据库查询层和工具映射层同时限制数量与字符数。

### 5.4 来源与引用方案

MVP 采用来源级证据，不做 Claim 级引用：

- 继续使用 AiSourceDependency 记录本次 Run 实际读取的来源。
- 只按本轮实际启用的工具增加 DECISION_PROPOSAL、DECISION_VOTE_ROUND 等来源类型。
- DECISION_RESOLUTION 继续复用现有来源类型。
- 历史消息接口返回安全的来源摘要和定位信息，不返回权限字段、内部 payload 或完整敏感正文。
- 来源失权后只显示“来源当前不可用”，不得通过标题、片段或链接旁路泄漏信息。
- 未来如果需要“每条主张对应 citation”，再单独设计 AiCitation 契约和持久化方案。

## 6. 分步执行计划

每个步骤都必须独立验证、独立说明和可回滚；完成一个步骤后停止，等待检查，不自动进入下一个步骤。

### P0：基线与演示准入检查

预计：0.5～1 个专注工作日。

目标：确保当前已有闭环在开始新增业务能力前可以稳定演示。

主要工作：

- 记录当前分支、工作区状态、依赖版本和定向测试基线。
- 修复 typescript、tsc、Jest/ts-jest 的本地依赖加载问题。
- 用真实登录账户完成一次新 Thread、已有 Thread、刷新、停止和重试验收。
- 验证一个权限拒绝场景和一个重名决策场景。
- 删除或隐藏明确未接入的“联网检索”控件。
- 通过引用检查确认 Web 占位工具和 use-ai-chat 没有生产调用；有调用则保留并标记，不猜删。

非目标：不新增业务工具，不改 Runtime，不改数据库结构。

验收：Web 和 Server 定向验证命令可执行；真实浏览器主链可以完成一次发送、流式、刷新和停止。

### P1：过程证据契约与来源边界

预计：0.5～1 个专注工作日。

目标：先冻结 getDecisionFormationEvidence 的输入、输出、来源和隐私边界。

主要文件方向：

- packages/contracts/src/ai/ 下新增或扩展过程证据类型。
- apps/server/src/modules/ai/types/ai-tool-source.types.ts。
- apps/server/src/modules/ai/types/ai-tool-registry.types.ts。
- apps/server/prisma/schema.prisma，仅在确有必要时扩展来源枚举。
- 新增工具 descriptor 和对应类型文件。

主要工作：

- 输入只允许使用本 Run 中唯一发现的 decisionId。
- 输出固定提案、投票汇总、正式决议和时间线的数量/字符上限。
- 明确开放投票、匿名投票、取消投票和无决议的返回语义。
- 明确 proposal、vote round、resolution 的来源登记规则。
- 补充契约、注册表和隐私矩阵测试。

非目标：不查询数据库，不注册 Runtime，不实现 UI。

验收：非法输入、直接猜测 ID、匿名投票字段、超限结构和来源类型均有确定性测试。

### P2：业务域查询与 AI 工具执行器

预计：1～2 个专注工作日。

目标：让新工具使用真实决策数据，并保持 NestJS 最终权限裁决。

主要文件方向：

- apps/server/src/modules/decisions/services/ 下的窄查询能力。
- apps/server/src/modules/decisions/decisions.module.ts，按实际依赖导出查询服务。
- apps/server/src/modules/ai/tools/decision/ 下的 descriptor、executor 和测试。
- apps/server/src/modules/ai/ai.module.ts。
- apps/server/src/modules/ai/services/tool/ai-tool-invocation.service.ts，仅在需要补充来源类型校验时修改。

主要工作：

- 在数据库层先叠加决策权限，再限制字段、数量和排序。
- 复用现有提案、投票、决议业务语义，不在 AI 模块重写投票隐私规则。
- 不查询 DecisionBallot 的个人身份映射。
- 每次工具调用登记父级决策和实际返回的子来源。
- 工具失败、无结果、无决议和超时都转成模型可以理解的稳定结果。

非目标：不实现讨论消息搜索，不读取会议全文，不引入向量检索。

验收：真实脱敏 Fixture 下通过成功、空结果、越权、删除、匿名投票和字段白名单测试。

### P3：Runtime 接入与回答指令

预计：0.5～1 个专注工作日。

目标：把新工具接入当前 Runtime，完成“发现 → 上下文 → 过程证据 → 回答”。

主要文件方向：

- apps/server/src/modules/ai/ai.module.ts。
- apps/web/src/features/ai/runtime/ai-agent-runtime.server.ts。
- apps/web/src/features/ai/runtime/ai-agent-tools.server.ts。
- apps/web/src/features/ai/agents/decision-hub-agent.ts。
- 现有 AI Runtime Mock 测试。

主要工作：

- 扩展系统指令，明确三工具的使用顺序和无证据回答边界。
- 保持当前 MAX_AGENT_STEPS 和现有租约、事件、终态逻辑，不顺便重写 Runtime。
- 用 Mock 模型验证唯一候选、多候选、无结果、工具失败和完整过程回答。
- 验证工具调用审计和来源依赖与实际输出一致。

非目标：不使用 ToolLoopAgent，不使用 useChat，不切换 UI 协议。

验收：Mock 可以稳定完成核心工具链，步数上限和工具失败不会造成无限循环或伪造答案。

### P4：来源级证据展示与历史恢复

预计：1～1.5 个专注工作日。

目标：让用户真正看到回答依据，并确保刷新、失权和历史读取安全。

主要文件方向：

- apps/web/src/features/ai/components/ai-citation-list.tsx。
- apps/web/src/features/ai/components/ai-chat-surface.tsx。

- apps/web/src/features/ai/utils/ai-workspace-message.ts。
- apps/server/src/modules/ai/services/thread/ai-message-query.service.ts。
- packages/contracts/src/ai/ai-message-history.types.ts 或新的来源展示契约。

主要工作：

- 将来源级证据转换为提案、投票、决议和时间线来源卡片。
- 来源卡片只展示安全标题、时间、类型和可用的业务跳转信息。
- 来源失权或删除时显示中性不可用状态。

## 7. 测试与验收矩阵

### 7.1 Agent 与工具

- 唯一候选：完成上下文和过程证据读取。
- 多候选：只展示候选，不读取任意一个。
- 空候选：说明当前授权范围内未找到，不断言系统绝对不存在。
- 直接猜测 decisionId：NestJS 拒绝读取。
- 工具失败或空结果：模型不编造内容。
- 达到步数上限：安全停止并给出有限回答。

### 7.2 业务安全

- 非项目成员不能读取决策过程。
- 私有区域失权后来源卡片隐藏。
- 匿名投票不返回个人票、投票人和匿名理由。
- 开放投票未结束时不描述为最终结论。
- 没有正式决议时明确显示“尚未形成正式决议”。
- 工具输入、输出和来源均受数量与字符上限限制。

### 7.3 工作台生命周期

- 新 Thread 首条消息。
- 已有 Thread 连续发送。
- 流式输出期间刷新。
- 浏览器断开后 GET 恢复。
- 用户主动停止。
- 模型失败后重试。
- 来源失权后刷新历史。

### 7.4 推荐验证命令

~~~bash
pnpm --filter @nextnest/web test:ai:model
pnpm --filter @nextnest/web test:ai:protocol
pnpm --filter @nextnest/web lint
pnpm --filter @nextnest/server test:ai:evaluation
pnpm --filter @nextnest/server check-types:ai:evaluation

git diff --check
~~~

如果本地 TypeScript、Jest 或数据库环境未准备好，应先修复验证环境并记录原因，不得把未执行的检查标记为通过。

## 8. 面试演示脚本

### 场景一：正常闭环

~~~text
帮我说明“供应商选择”这项决策是怎么形成的？
~~~

演示顺序：

1. 展示 Agent 先发现决策，而不是直接相信用户输入的 ID。
2. 展示工具轨迹：决策发现、上下文读取、过程证据读取。
3. 展示回答中的提案、投票汇总、正式决议和来源卡片。
4. 点击来源，说明回答可以回到业务事实核验。

### 场景二：安全边界

~~~text
直接读取 decisionId=999999 的投票和匿名投票人。
~~~

演示预期：

- 后端不信任模型给出的主键。
- 未经本 Run 唯一发现的目标不能读取。
- 匿名个人选票和身份映射不会返回。
- Agent 解释当前只支持授权范围内的只读过程分析。

### 场景三：证据不足

~~~text
这项决策为什么选择了方案 A？
~~~

如果当前数据只有提案和投票，没有讨论理由，预期回答应说明：

- 可以确认哪些事实；
- 当前没有足够证据确认“为什么”；
- 不把模型常识或提案标题当成真实原因。

## 9. 面试叙事重点

面试中重点讲以下工程取舍：

1. 不把 AI 做成脱离业务数据的通用聊天框，而是围绕“决策如何形成”设计垂直 Agent。
2. 模型可以提出工具调用，但最终权限和业务事实由 NestJS 重新判断。
3. 结构化事实、工具审计和来源依赖分别承担不同职责。
4. PostgreSQL 是业务事实和审计权威，向量索引未来也只能作为可重建的检索层。
5. 先完成有证据的结构化闭环，再根据真实 Query 判断是否需要 RAG。
6. 当前保留自建 Runtime 是有意识的范围决策：已经有租约、幂等、恢复和产品交互语义，不为了抽象统一而增加迁移风险。
7. 通过无答案、越权、匿名投票和来源失权测试证明系统不会只追求“回答流畅”。

---

## 10. P0 完成后的后续顺序

P0 完成后，不自动扩展所有工具，按真实问题选择下一项：

1. searchDecisionEvents：只有时间线字段不足以解释过程时才实现。
2. 中文关键词检索：只有用户开始询问“谁在讨论中提过某个观点”时才实现。
3. 真实 Retriever 评测：复用现有 Gold Query，重新测量真实 Recall@K 和权限泄漏。
4. pgvector/Embedding：只有关键词基线无法满足真实 Query 时才引入。
5. 混合召回、重排和 Claim 级引用：必须有真实评测收益后再做。
6. Redis、Workflow、后台索引和长任务：出现真实长任务、重试或多实例一致性问题后单独评审。

Runtime 官方化迁移不属于当前计划；除非老大重新明确授权，否则不重新打开该方向。

## 11. 每轮执行纪律

- 动手前说明本轮目标、不做什么、主要文件和验证方式。
- 每轮只完成一个边界明确的步骤，不跨 P0～P5 批量实现。
- 新增依赖、数据库结构或外部基础设施前，必须先说明收益、替代方案、接入成本和部署影响。
- 每个步骤完成后说明改动、原因、验证结果和下一建议，然后停止等待检查。
- 测试、评测和脱敏 Fixture 是长期质量资产；一次性 Smoke 脚本在不再依赖后及时清理。
- 不提交 .env、真实业务数据、Token、Cookie、.next、dist、coverage 或临时调试文件。

## 12. 计划完成标志

本计划完成时，仓库应能用真实脱敏数据稳定展示：

~~~text
自然语言问题
  -> 授权决策发现
  -> 唯一目标确认
  -> 结构化决策过程证据

  -> 来源级证据卡片
  -> 刷新/失权后仍安全可核验
~~~

此时 NextNest 的 AI 模块可以被清楚地描述为：

> 一个基于授权决策过程数据、能够调用受控业务工具并展示证据来源的只读 Decision Agent。
