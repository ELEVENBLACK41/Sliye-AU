# 首条纵向用户故事评测合同

> 本文档用于锁定 NextNest AI 的第一条可评测纵向用户故事，作为评测数据和实现的共同边界；具体 TypeScript、Fixture、指标与报告位于同目录，仍不包含生产 Agent 逻辑。

## 用户故事与评测目的

当一名当前有权访问某项决策的登录用户提出“这项决策如何形成”时，系统应基于该用户**当前有权访问**的决策过程记录，生成一份可核验的过程说明草稿。说明的目标是帮助用户回看一项正式决议从讨论、提案、投票到形成决议的过程，而不是替代业务事实、编造未发生的过程，或推动决议后的执行。

本用户故事的评测目的，是验证系统能否在权限和证据约束下：

- 还原有证据支持的决策过程；
- 呈现对形成决议有实质影响的分歧与节点；
- 准确说明最终结果；
- 在证据缺失或不可访问时明确说明边界；
- 让每个结论回到用户可访问的原始记录核验。

若某项需求不能服务于上述“解释一项既有决策如何形成”的闭环，或要求系统改变既有业务记录，则不属于本合同，应另行确认用户故事和评测边界。

## 输入前提

一次符合本合同的请求必须同时满足以下前提：

1. 存在一项 `Decision`，且该决策已有讨论、提案、投票和正式决议等过程材料。
2. 当前请求来自已登录用户；该用户提出的问题等价于“这项决策如何形成”。
3. 后端能够根据当前身份与业务权限，确定该用户可访问的决策范围、讨论区域和证据来源。
4. 可用材料中允许同时包含结构化事实（例如提案、投票汇总、正式决议与事件）和讨论证据；它们各自只能用于其能够证明的内容。

这里的“已有”表示评测 Fixture 或真实受控数据已经具备相应过程记录，并不允许系统为了完成回答而补写讨论、提案、投票或决议。

## 输出合同

输出是供用户查看、继续编辑的过程说明草稿，至少应包含以下内容；任何内容都不能脱离证据单独成立：

| 输出部分     | 必须回答的内容                                                         | 证据要求                                                         |
| ------------ | ---------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 过程概览     | 用简明顺序说明从讨论、提案、投票到正式决议的形成过程。                 | 对关键过程事实逐条引用。                                         |
| 关键分歧     | 说明支持、反对、保留意见或提案差异中，确有记录且与决策形成相关的部分。 | 不能把单一观点表述为共识；涉及的判断必须有来源。                 |
| 关键节点     | 标明可从记录核验的转折点，例如提案提出、投票结束或正式决议形成。       | 时间、事件与状态以结构化事实或对应原始记录为准。                 |
| 最终结果     | 明确正式决议与允许公开的投票汇总结果。                                 | 不以讨论推测替代正式决议或投票汇总。                             |
| 证据不足说明 | 对缺失、矛盾、不可访问或无法支持的部分，明确说明不能确认什么以及原因。 | 不得以推测补全；无足够证据时应部分回答或拒答。                   |
| 逐条引用     | 为主要结论提供可定位的来源，使用户可以逐项核验。                       | 每条引用都必须可访问、未删除，并指向本次允许证据集中的原始记录。 |

“逐条引用”是结论与来源之间的可检查关系，不是仅在段落末尾笼统列出若干材料。引用应足以让评测者判断该来源是否实际支持对应结论。

## 明确非目标

本合同只解释决策形成过程，明确不包含以下行为：

- 生成、分配或管理决议后的任务、行动项；
- 修改、补录、推断个人明细或以任何形式影响既有投票；
- 替用户发布、确认或写入正式决议；
- 执行跟踪、进度管理、结果验收或其他超出当前产品边界的决议后闭环。

即使用户在提问中要求上述操作，本用户故事的正确行为也是维持只读的过程说明边界，而不是将请求扩展为写操作或执行管理。

## 权限与证据不变量

以下不变量是本合同的硬性验收条件；任一项被破坏，即使生成文本流畅也视为失败：

1. **NestJS 后端最终裁决权限。** 前端、Agent 参数、用户提示或模型判断都不能替代 NestJS 对当前用户、决策和证据范围的授权判断。
2. **先权限过滤，后召回。** 只可在已获准的数据范围内查询、检索和组装证据；不得先取得私有材料再依赖模型隐藏。
3. **匿名投票仅使用汇总。** 对匿名投票，只能使用后端允许公开的汇总结果；不得检索、展示、推断或关联到个人匿名选票。
4. **无证据不编造。** 无法取得充分证据支持某个关键事实时，必须明确说明证据不足、给出可支持的有限内容，或拒绝回答相应部分。
5. **引用持续可核验。** 每条引用在交付时都必须属于当前用户可访问、尚未删除的原始来源；不可访问、已删除或不在本次允许证据集中的来源不得出现在回答中。

## 与后续评测工作的关系

本合同先定义“第一条用户故事是否做对”，后续工作必须以它为上位边界：

- **Gold Query**：围绕本故事构造中文问题，分别覆盖过程、分歧、节点、结果、无答案与权限边界；每条 Query 再标注允许来源、禁止来源、答案要点与是否应拒答。
- **Fixture**：提供脱敏且可重复的决策过程材料，用来稳定复现本合同中的正常、证据不足、私有区域和匿名投票等情形；不提交真实私聊内容。
- **评测层**：分别衡量检索是否找到允许的相关证据且不泄漏、回答是否忠实并有充分引用，以及系统工具选择、延迟、成本、取消和降级行为是否符合约束。

这些产物都不得改变本合同的输入、输出、非目标和不变量；它们只负责将本合同转化为可执行数据、检查与报告。

## 第 0 阶段落地结构

```text
evaluation/
  fixtures/
    decision-process/        # 三个完整脱敏决策形成案例
    gold-queries/            # 按问题分类拆分的 45 条 Query
    private/                 # 真实受控样本，仅本地使用且已 Git 忽略
  metrics/                   # Retriever、Answer、System 三层纯指标
  reports/                   # 版本化 JSON/Markdown 报告
  runners/                   # 权限过滤、V4 Mock 运行和报告生成
  types/                     # Gold Query、Fixture、观察值和报告合同
  ai-evaluation.spec.ts      # 数据、泄漏、指标和确定性门禁
```

首版数据集共 50 条中文 Gold Query：精确事实 8 条、时间线 8 条、语义 8 条、比较 7 条、否定或无答案 7 条、权限 5 条、对抗 7 条。每条都包含请求范围、预期授权、相关来源、禁止来源、答案要点和拒答标记。

## 运行方式

```bash
pnpm --filter @nextnest/server test:ai:evaluation
pnpm --filter @nextnest/server check-types:ai:evaluation
pnpm --filter @nextnest/server ai:evaluation:report
```

报告命令会从同一次确定性运行生成：

- reports/stage-zero-evaluation-report-v1.json
- reports/stage-zero-evaluation-report-v1.md

## Mock 基线边界

- 使用仓库锁定的 ai@7.0.18，实际调用 MockLanguageModelV4 和 MockEmbeddingModelV4。
- 语言模型输出、向量、Token、延迟、取消和降级场景均固定，不访问真实模型，也不产生费用。
- 关键词、向量和混合检索是为了验证指标及门禁而准备的 Fixture 模拟排序，不代表生产 RAG 效果。
- 接入真实 Retriever 或模型后，必须复用同一 Gold Query、指标和报告结构重新生成基线，不能沿用 Mock 数值宣称生产质量。
- 真实业务样本只能放在已忽略的 fixtures/private/，不得提交私聊、Token、Cookie 或其他敏感信息。
