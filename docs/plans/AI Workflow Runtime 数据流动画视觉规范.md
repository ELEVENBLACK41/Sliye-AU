# Decision Hub AI Workflow Runtime 数据流动画视觉规范

> 本文档用于记录 Decision Hub AI Workflow Runtime 的运行拓扑、数据流动光线和异常状态视觉规则，服务于后续交互式 Runtime Graph 的设计与实现。

## 1. 文档定位

- 状态：视觉与交互规范草案
- 适用范围：AI Agent 运行过程的拓扑图、Context Bus、Tool Call、检索链路、证据链路和运行日志可视化
- 核心目标：让用户通过节点位置、连接关系和流动光线，理解 AI 当前执行到了哪里，以及数据正在流向哪个节点
- 当前边界：只呈现一次决策如何形成的过程，不扩展到决议形成后的任务分配、执行跟踪和结果验收
- 参考方向：高密度 AI Runtime 拓扑图，允许节点分布不规则、连线交叉和局部混沌，但不能出现与真实运行无关的装饰性连线

## 2. 核心视觉结论

Runtime Graph 不是普通 BPMN 或低代码 Workflow。

它应该表现为一次正在发生的 AI Run：

~~~text
过去：完成过的路径保留低亮度余辉
当前：正在传输的数据用一段发光线束从起点流向终点
未来：等待执行的路径保持低透明度，不播放动画
~~~

画布允许出现大量白色连接线、交叉关系和多个并行数据流。中央 RUN CONTEXT BUS 是共享运行上下文的可视化抽象，不应表现成 Redis、Kafka、数据库或传统消息队列。

## 3. 连接线的视觉层级

### 3.1 基础连接线

所有连接线默认使用白色系，不使用彩色连接线。

| 连接状态 | 视觉表现 | 是否播放动画 |
| --- | --- | --- |
| 未执行 | 暗灰白、低透明度、细线 | 否 |
| 等待执行 | 灰白色、略高于未执行状态 | 否 |
| 已完成 | 亮白色、保留轻微余辉 | 动画结束后停止 |
| 当前传输 | 亮白色底线 + 发光线束 | 是 |
| 调用压力升高 | 发光线束由白色逐步变为暖黄色 | 是 |
| 失败路径 | 红色底线或红色发光线束 | 仅在失败事件发生时播放 |

### 3.2 线的真实含义

一条线应代表真实的运行关系，例如：

- Agent 读取 Context Bus 中的决策上下文
- Agent 调用某个具体 Tool
- Tool 将结果写回 Context Bus
- Keyword Retrieval 或 Vector Retrieval 将候选集提交给 RRF Fusion
- RRF Fusion 将融合结果提交给 Rerank
- Evidence Check 将通过的证据提交给 Citation Mapper

如果一条线只是“可能存在的依赖关系”，不应播放流动光线，只展示为低亮度静态线。

## 4. 发光线束，而不是光点

### 4.1 定义

当前数据流使用一段短的白色发光线束沿连接线移动，不使用单独的圆形光点。

视觉效果类似：

~~~text
普通连接线：────────────────────────

流动状态：  ───────▰────────────────→
                   发光线束
~~~

发光线束具有以下特征：

- 线束本身是短线段，占整条路径长度的一小部分
- 线束从连接线起点移动到终点
- 线束前后有柔和白色辉光
- 线束移动方向必须清晰
- 线束走完一次后停止，不循环常亮
- 底层连接线仍然保留，用于表示路径本身

### 4.2 单条连接线的排队规则

同一条连接线上同一时刻只允许出现一个发光线束。

如果调用持续产生新的数据包，后续数据必须进入队列：

~~~text
packet-001 ───────────────→ 播放完成
packet-002 ───────────────→ 等待后播放
packet-003 ───────────────→ 继续排队
~~~

禁止出现以下效果：

~~~text
同一条线上多个发光线束互相重叠、无限循环或无序闪烁
~~~

不同连接线之间可以并行播放：

~~~text
Edge A：──────▰────────────→
Edge B：────────▰──────────→
Edge C：▰───────────────────→
~~~

因此最终规则是：

> 一条线一次只能有一个发光线束；多条线可以同时各自播放一个发光线束。

### 4.3 单次播放流程

~~~text
Runtime Event 到达
  ↓
找到对应 Edge
  ↓
将数据包加入该 Edge 的 pending queue
  ↓
如果当前没有播放中的线束，则立即开始播放
  ↓
发光线束从起点移动到终点
  ↓
动画结束，写入到达时间和完成状态
  ↓
如果队列中还有数据包，则播放下一个
~~~

动画不应使用永久循环。动画完成事件是取出下一个数据包的唯一触发点。

## 5. 光线颜色规则

### 5.1 正常运行：白色

正常数据流使用白色或半透明白色：

- 底线：低亮度白色
- 当前线束：高亮纯白
- 辉光：柔和白色
- 已完成路径：较暗的白色余辉

白色是整个 Runtime Graph 的主色，不应被其他颜色抢走视觉焦点。

### 5.2 调用压力升高：渐变为黄色

当某条调用链的压力逐步升高时，发光线束从白色平滑转为暖黄色。

压力不等于失败。黄色只表示当前调用变慢、排队变长或资源接近阈值。

建议的压力信号包括：

- 同一 Edge 的待处理数据包持续堆积
- Tool Call 的 P95 延迟升高
- Agent 同时运行的 Tool 数量升高
- Retrieval 候选集数量快速增长
- Token 消耗速度超过预期
- 重试次数增加
- 外部 Tool 返回限流或拥塞提示，但尚未失败

建议的状态分段：

| 压力等级 | 视觉表现 | 说明 |
| --- | --- | --- |
| 正常 | 纯白线束 | 数据流畅，队列短 |
| 轻度压力 | 白色向暖白过渡 | 开始出现排队或延迟升高 |
| 中度压力 | 暖白向黄色过渡 | 调用压力明显，需要关注 |
| 高压力 | 明显黄色线束 | 队列或延迟接近阈值 |
| 失败 | 红色线束或红色闪烁 | 调用已经失败，不再使用黄色表示 |

颜色变化应该是连续过渡，而不是突然从白色跳成黄色。

### 5.3 失败路径：红色

失败只使用少量红色，避免整个画布变成告警面板。

失败发生时：

1. 当前正在播放的线束可以完成当前路径，或根据事件类型立即中断
2. 失败路径播放一次红色发光线束
3. 对应节点显示 FAILED
4. 失败线保留红色低亮度余辉
5. 如果存在自动重试，重试路径恢复为白色或黄色
6. 如果重试仍然失败，才再次播放红色失败线束

红色只表达已经发生的失败，不表达普通压力、等待或排队。

## 6. Runtime Event 与动画的关系

动画必须由真实运行事件驱动，而不是完全由前端随机播放。

建议事件类型：

~~~text
agent.plan.created
context.read.started
context.read.completed
tool.call.started
tool.call.completed
tool.call.failed
retrieval.batch.started
retrieval.batch.completed
evidence.selected
citation.mapped
draft.generated
~~~

每个事件至少需要能够定位：

- runId
- edgeId
- sourceNodeId
- targetNodeId
- eventId
- occurredAt
- duration
- status
- pressure
- payloadType

建议的运行状态结构：

~~~ts
type RuntimeEdgeState = {
  edgeId: string
  status: 'idle' | 'streaming' | 'completed' | 'failed'
  pressure: number
  activePacketId: string | null
  pendingPacketIds: string[]
}
~~~

其中 activePacketId 用于保证一条线同一时刻只有一个发光线束，pendingPacketIds 用于保存后续排队的数据包。

## 7. 画布密度与并行动画

画布可以存在大量节点和连接线，尤其在以下阶段：

- Decision Agent 同时调用多个 Tool
- 多个 Tool 同时读取或写入 Context Bus
- Keyword Retrieval 与 Vector Retrieval 并行
- 多批检索结果汇入 RRF Fusion
- 多组 Evidence 同时进入 Evidence Check

在高峰期，允许出现大量同时运动的线束。但每条线必须遵守单线单束规则，不能为了“看起来热闹”而脱离 Runtime Event 随机制造流量。

建议的视觉策略：

- 保留大量静态暗线，表达完整拓扑
- 让真实活跃的 Edge 播放线束
- 让压力较高的 Edge 播放黄色线束
- 让已完成 Edge 停止动画，只保留余辉
- 让 Context Bus 周围成为数据汇聚最密集的区域
- 控制同一时间高亮的颜色种类，主色仍然是白色

## 8. 推荐实现技术

### 8.1 图结构与拖拽

建议使用 @xyflow/react：

- 节点使用自定义 React Component
- 连接线使用自定义 SVG Edge
- 节点拖拽后由图引擎自动更新连接线位置
- Context Bus 使用带多个 Handle 的自定义节点
- Node Inspector 根据选中节点展示运行详情

### 8.2 线束动画

建议使用 SVG 双层 Path：

~~~text
底层 Path：表示连接关系
上层 Path：表示当前移动中的发光线束
~~~

上层 Path 使用 stroke-dasharray 和 stroke-dashoffset 做单次移动动画，并在 animationend 后处理队列中的下一个数据包。

不建议用单独的圆形光点替代线束，也不建议给所有 Edge 使用无限循环动画。

### 8.3 状态管理与事件接入

- Zustand：保存节点位置、Edge 状态、压力值和单线队列
- WebSocket 或 SSE：接收实时 Runtime Event
- CSS Animation 或 Web Animations API：播放短线束动画
- React Flow：负责节点拖拽、视口、选中和连接关系

如果以后需要同时渲染上千条边和大量发光线束，再评估将 Edge Layer 迁移到 Canvas/WebGL；第一阶段不需要为了规模预估而直接引入复杂渲染引擎。

## 9. 验收标准

### 9.1 视觉验收

- 画布中存在大量真实拓扑连线，不是少量规整流程块
- 节点可以不规则分布，连线允许交叉和汇聚
- RUN CONTEXT BUS 视觉上是共享上下文中心
- 当前执行路径可以通过移动中的发光线束快速识别
- 发光线束是短线段，不是圆点
- 同一条线同时只存在一个发光线束
- 多个事件到达时可以按顺序排队播放
- 正常运行使用白色
- 压力升高时白色平滑过渡为黄色
- 失败路径使用红色

### 9.2 运行验收

- Tool Call 开始时，对应调用路径进入播放队列
- Tool Call 完成时，对应结果路径进入播放队列
- 多个 Tool 并发时，不同路径可以同时播放
- 同一条路径连续收到多个事件时，不发生线束重叠
- 动画完成后能够继续播放队列中的下一个事件
- 页面暂停时，新事件可以暂存，但不继续播放动画
- 页面恢复后，队列可以继续消费
- Replay 时按照事件时间顺序重新播放
- 失败事件能够区分普通压力和真实失败

### 9.3 性能验收

- 拖拽节点时连接线跟随，不出现明显延迟
- 高密度连线下，节点选中和 Inspector 打开保持流畅
- 不因为每一帧动画而让整个节点树重新渲染
- 同一时间只更新发生变化的 Edge
- 动画数量达到上限时，有降级策略，例如降低辉光、降低线束数量或暂停非关键线束

## 10. 非目标

当前规范不包含：

- 决议形成后的任务分配
- 行动项执行进度
- 任务验收
- 普通 BPMN 审批流
- Redis、Kafka 或数据库监控面板
- 与真实 AI Run 无关的装饰性随机连线

本规范的核心是：

> 用大量真实的连接关系表达复杂 AI Runtime，用单线单束、按事件排队的发光线束表达数据正在流动，用白色、黄色和红色表达正常、压力和失败三种运行状态。
